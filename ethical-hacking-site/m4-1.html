Routers

Infrastructure
A router is a networking device that connects two or more packet-switched networks and forwards data packets between them, choosing the best path toward the destination.

F Core Functions

  • Packet forwarding — switch packets from ingress to the correct egress interface.
  • NAT (Network Address Translation) — rewrite source/destination addresses, sharing one public IP across a private range.
  • Packet filtering / ACLs — permit or deny traffic by rule (address, port, protocol).
  • Interconnecting technologies — link Ethernet, serial, fiber, wireless segments.
  • Path selection — pick the "best" route to a destination.
  • Dynamic routing — learn routes via OSPF (interior) and BGP (inter-AS).
  • QoS — prioritize latency-sensitive traffic (voice/video).
  • VLAN segmentation and acting as a DHCP server.

A Architecture

  • Input interface — receives packets, performs MAC/CRC check, looks up the forwarding table.
  • Routing processor (control plane) — runs routing protocols, maintains the routing/forwarding table, enforces ACLs.
  • Output interface — queues and transmits packets toward the next hop, applying QoS/shaping.

In high-end routers the data plane (forwarding) is often hardware-accelerated while the routing processor handles the control plane.

S Security Challenges

  • Firmware vulnerabilities — embedded code flaws; patch regularly via vendor updates.
  • DDoS on infrastructure — volumetric / protocol attacks saturate the router, blackholing legitimate traffic.
  • Default admin credentials — shipped admin/admin logins left unchanged give full takeover; change them and disable remote management.

Firewall

Perimeter
A firewall is a network security system that monitors and filters incoming/outgoing traffic according to a security policy — acting as a barrier between an internal (trusted) network and an untrusted network such as the internet.

Firewall Generations

1 Gen 1 — Virus

1980s. Threat was the computer virus; the response was antivirus software scanning files/signatures.

2 Gen 2 — Network

Mid-1990s. Threat moved to the network; the firewall was born to filter traffic at the perimeter.

3 Gen 3 — Application

2000s. Application-layer attacks drove IPS (Intrusion Prevention Systems) to inspect/block at L7.

4 Gen 4 — Payload

~2010. Targeted payloads & bots; defense added anti-bot and sandboxing to detonate unknown files.

5 Gen 5 — Mega

~2017. Large-scale, multi-vector "mega" attacks; advanced threat prevention (AI/threat-intel) is required.

+ NGFW

Next-Gen Firewall = the culmination: deep packet inspection + application-level control, and it integrates IPS inline.

Firewall Types

Packet Filtering

Stateless inspection of packets against ACLs (source/dest IP, port, protocol). Fast, cheap, but blind to connection state.

Proxy Service (Application-Layer)

Acts as an intermediary; the client talks to the proxy, the proxy fetches on its behalf. Full L7 visibility, can filter content, but slower.

Stateful Inspection

Tracks the state of active connections (state table) and makes decisions based on context — not just individual packets.

NGFW (Next-Gen Firewall)

Adds deep packet inspection and application-level awareness (user/app identity, threat feeds). A true NGFW integrates IPS.

Honeypots

Deception
A honeypot is a security resource whose value lies in being probed, attacked, or compromised — a decoy system that lures, deflects, and studies attackers while appearing to be a high-value asset (database, server, router).

Placement

  • DMZ — exposed segment between firewall and internet; common, realistic exposure.
  • Outside the firewall — to study raw internet attack traffic with no filtering.

Scale-out terms

  • Honeynet — a network of two or more honeypots working together.
  • Honey farm — a centralized collection of honeypots managed from one place.

Types

Production vs Research

Production honeypots protect an organization (added risk detection). Research honeypots gather threat intelligence (used by vendors/analysts).

Pure / High-Interaction

A full real system with real services and often root access to the attacker. More realistic data but riskier — a compromise can be used to pivot.

Low-Interaction

Simulates common attack vectors only (e.g. Honeyd). Safe, cheap, easy to deploy; great for detecting bots/automated malware but gives less depth.

Specialized Honeypots

Malware honeypot

Collects and analyzes malware binaries.

Spam honeypot

Traps spam/abuse (open relays, spam sinks).

Database honeypot

Decoy DB to catch SQL injection/data theft.

Client honeypot

Proactively seeks out malicious servers (drives a client to detect drive-by attacks).

Benefits & Disadvantages

Benefits

  • Real data — captures actual attacker behavior.
  • Fewer false positives — any interaction is by definition suspicious.
  • Cost-effective — cheap relative to full IDS tuning.
  • Encryption circumvention — attackers decrypt/operate in clear once inside the decoy.

Disadvantages

  • Limited data — only sees what hits the honeypot.
  • Isolated — no view of the full enterprise.
  • Distinguishable — skilled attackers may detect the decoy.
  • Can risk production — a high-interaction compromise can be used to pivot into real systems.

IDS vs IPS

Detection / Prevention
IDS (Intrusion Detection System) is passive: it watches traffic, detects suspicious activity and raises an alert — it does not block. IPS (Intrusion Prevention System) sits inline in the traffic path and can block or stop malicious traffic in real time.
DimensionIDS (Detection)IPS (Prevention)
PositionOut-of-band (span/monitor port)Inline (must see & forward traffic)
ActionAlert / log onlyBlock / drop / reset connection
Latency impactNone (passive)Adds processing latency (inline)
Risk if it failsMisses detectionCan become a bottleneck / single point of failure
Best forVisibility, forensics, complianceActive blocking of known/likely attacks

IDS Classifications

By placement / scope

  • NIDS — Network-based; watches network segments.
  • HIDS — Host-based; watches a single host (files, logs, syscalls).
  • PIDS — Protocol-based; monitors a protocol/interface.
  • APIDS — Application-specific; watches app-layer (e.g. DB queries).
  • Hybrid — combines multiple sensors / correlation.

By detection method

  • Signature-based — matches known attack patterns (like AV signatures); fast but blind to new attacks.
  • Anomaly-based — flags deviations from a learned "normal" baseline; can catch novel attacks but more false positives.

IPS Classifications

By placement

  • NIPS — Network IPS (inline at a network point).
  • WIPS — Wireless IPS (monitors/blocks rogue APs & wireless attacks).
  • HIPS — Host IPS (blocks on the endpoint).

By technique

  • NBA (Network Behavior Analysis) — watches traffic for anomalous behavior across the network.
  • Signature, statistical-anomaly, and stateful protocol analysis (validates protocol-state conformance) are the three common analysis methods, shared with IDS concepts.

Web Filtering

Content Control
Web filtering is the practice of controlling which web resources users may reach — it can allow or block content by category, domain, or policy.

Allow-list vs Block-list

  • Allow-list (whitelist) — only explicitly approved sites are reachable; maximum security, low usability.
  • Block-list (blacklist) — everything allowed except known-bad sites; higher usability, gaps remain.

Filtering techniques

  • DNS filtering — resolve or sinkhole domains at the DNS layer.
  • URL filtering — match the requested URL/path against categories or patterns.
  • Content filtering — inspect page content (keywords, MIME, policies).

Server-side vs Client-side

  • Server-side — enforced at a proxy/gateway (central, harder to bypass).
  • Client-side — enforced on the endpoint (browser/agent); easier for users to tamper with.

Why filter the web?

  • Malware protection — block drive-by / exploit sites.
  • Data security — stop exfiltration to webmail/cloud.
  • Compliance — meet regulatory / acceptable-use rules.
  • Policy — enforce acceptable-use and productivity rules.

Web Server

Application
A web server is the hardware + software that stores, processes and delivers web content using the HTTP/HTTPS protocol.

Request flow (how a page loads)

  1. User enters a URL in the browser.
  2. Browser performs a DNS lookup to resolve the domain to an IP.
  3. Browser sends an HTTP request to the server (e.g. GET /index.html).
  4. Server processes it and returns an HTTP response (status + headers + body).
  5. Browser renders the content.

Static vs Dynamic content

  • Static — pre-built files served as-is (HTML, CSS, images).
  • Dynamic — generated on the fly by server-side code (e.g. ASP / PHP) pulling from a database.

Common servers & capabilities

  • Apache, IIS, Nginx, Lighttpd, Sun Java System (Web Server).
  • Can also handle SMTP / FTP and other protocols.
  • Run server-side scripting via ASP, PHP, etc. to build dynamic pages.

SQL Injection (SQLi)

Web Attack
SQL injection is a code-injection technique where an attacker inserts malicious SQL into an input field so the application executes it against the backend database, manipulating queries it was never meant to run.

In-band

Attacker uses the same channel for the attack and to read results.

  • Error-based — provoke DB errors that leak schema/info.
  • Union-based — UNION a malicious SELECT to append data to the page output.

Inferential / Blind

No data returned directly; the attacker infers answers from behavior.

  • Boolean-based — true/false responses reveal bits of data.
  • Time-based — inject WAITFOR/SLEEP() delays to extract data through timing.

Out-of-band

Results are exfiltrated over a different channel than the injection:

  • DNS — trigger the DB to resolve an attacker-controlled domain carrying data.
  • HTTP — make the DB issue an outbound HTTP request to the attacker.
Impact: attackers can view secret lists (dump users/credentials), delete or alter tables, and gain admin privileges — full compromise of the data tier.

Cross-Site Scripting (XSS)

Web Attack
XSS is a web vulnerability that lets a third party execute a script in the victim's browser — usually by injecting client-side code (JavaScript) that the site then serves to other users.

Reflected XSS

The malicious payload is embedded in the request and reflected back in the response. The script runs immediately when the victim opens a crafted link (e.g. a search box that echoes input). Not stored — it needs the victim to trigger it.

Stored XSS

The payload is saved on the server (database/comment field) and served to every user who views it — e.g. a comment thread that stores <script> which executes for everyone reading the comments. More dangerous because it hits many victims passively.

Note on DOM-based XSS

Although the PDF's primary two types are Reflected and Stored, a DOM-based variant is widely recognized in practice: the payload is executed by manipulating the Document Object Model in the victim's browser (client-side logic) rather than server output. Keep it in mind for real-world testing, but treat Reflected/Stored as the core exam pair.

Exploit Writing

Offensive
Writing an exploit is the process of turning a known vulnerability into reliable, repeatable code that subverts a program's intended behavior (typically to gain control of execution).

Workflow

  • 1. Identify the vulnerability — find the bug (overflow, format string, etc.).
  • 2. Attach a debugger — run the target under a debugger to observe registers/memory at the crash.
  • 3. Overwrite the return value — craft input so the saved return address is overwritten with a controlled value (the seed of control hijack).
  • 4. Automate — script the PoC with Perl / Python for repeatable delivery.
  • 5. Find a DLL address — locate a loaded module's (DLL) address containing useful instructions (e.g. JMP ESP) to redirect execution into the injected shellcode.

Outcome

Once the return address points at attacker-controlled memory and a reliable jump is found, the injected shellcode runs with the process's privileges — giving a shell, privilege escalation, or payload execution.

Reliability concerns: bad characters, address randomization (ASLR), and stack protections must be handled.

Buffer Overflow

Memory Corruption
A buffer overflow occurs when a program writes data that exceeds the allocated buffer's capacity, causing it to overflow into adjacent memory and overwrite other data or control structures.

System crash

Overwritten data corrupts execution → the process (or OS) crashes / becomes unstable.

Access-control loss

Overwriting permission/control data can defeat the program's intended security checks.

Further exploits

The overflow becomes the foothold for injecting and running attacker shellcode.

Arbitrary code execution: by overwriting a return address or function pointer, an attacker can redirect execution to their own code — the root cause behind most classic remote exploits (and the mechanism exploited in §9).

Reverse Engineering

Analysis
Reverse engineering (RE) is the process of analyzing a product — software or hardware — to understand its functions and information flow. In security it is heavily used for malware RE (understanding what malicious code does without source).

The PDF's three "stages"

The source lists these stages (notably framed around physical scanning of an object):

  • Scanning — capture the geometry / data of the target.
  • Point Processing — clean and process the captured point data.
  • Geometric Model — reconstruct a usable model from the processed points.

⚠ These are the PDF's literal stages and are kept here for fidelity, though they describe a 3D-scanning view of RE rather than code RE.

The standard security RE view

For malware/software RE, the practical stages are:

  • Information gathering — collect binaries, strings, metadata, packer info.
  • Disassembly / decompilation — turn machine code back into assembly / higher-level code.
  • Static + dynamic analysis — read code statically and run it in a sandbox to observe runtime behavior.
  • Documentation — record findings, IoCs, and the program's logic.

Tools

Debuggers (user-mode / kernel-mode)

  • IDA Pro — disassembler + debugger (industry standard).
  • OllyDbg — popular user-mode Windows debugger.
  • GDB — GNU debugger (Linux / native).
  • Immunity Debugger — exploit-dev oriented.
  • WinDbg — Microsoft kernel/user debugger.

Other RE tooling

  • Fault Injection tools — deliberately induce errors to expose behavior.
  • Disassembler — convert binary to assembly (often IDA/Radare2/Ghidra).
  • Decompiler — reconstruct higher-level (C-like) source from binaries.

Email Hacking

Account / Comms
Email hacking is the unauthorized access to, or manipulation of, someone's email account or messages — to read, send, or alter mail without permission.

Phishing

Fake messages trick users into revealing credentials or clicking malicious links.

Password guessing

Tries likely passwords (common/known) against the account.

Brute force

Systematically tries many password combinations until one works.

Malware

Keyloggers / trojans capture credentials or sessions on the victim's device.

Session hijacking

Steals an active session token/cookie to ride an authenticated session.

MITM

Man-in-the-Middle intercepts mail traffic on an insecure network.

Email spoofing

Forging the sender address so mail appears to come from someone else — used in phishing/BEC. Defenses: SPF, DKIM, DMARC to authenticate legitimate senders.

Incident Response

Process
Incident response is the organized approach to handling a security breach — detecting, containing, and recovering — to minimize damage, cost, and recovery time. Owned by the CSIRT (Computer Security Incident Response Team).

Step 1 — Early Detection

Spot the incident early, e.g. a SIEM alert flagging anomalous activity or an IDS/IPS alarm.

Step 2 — Analysis

Investigate: collect IoC (Indicators of Compromise), triage scope and severity.

Step 3 — Prioritization

Rank by business impact and urgency to decide response order.

Step 4 — Notification

Notify internal stakeholders and, where required, external parties (customers, regulators, partners).

Step 5 — Containment & Forensics

Stop the spread (isolate systems) while preserving evidence for forensic analysis.

Step 6 — Recovery

Eradicate the threat, rebuild clean systems, restore from trusted backups, and patch the root cause.

Step 7 — Incident Review

Post-mortem: document what happened, what worked, and improve detections/processes so the same incident doesn't recur.

Bluetooth Hacking

Wireless
Bluetooth hacking means locating Bluetooth-enabled devices and exploiting weaknesses in the protocol or its configuration to attack them.

Bluesmacking

A DoS attack abusing L2CAP — flooding the device with oversized/ping packets to crash or hang it.

Bluejacking

Sending unsolicited messages (usually just text/contact cards) to a victim's device — mostly annoying, low harm.

Bluebugging

Taking control of a device left in discovery mode — making calls, reading SMS, using features without permission.

Bluesnarfing

Stealing data (e.g. SMS, contacts, calendar) from a vulnerable device over the Bluetooth link.

Prevention

  • Turn Bluetooth off when not in use.
  • Reject unknown pairing requests.
  • Update firmware/OS to fix BT flaws.
  • Keep devices non-discoverable (hidden).
  • Unpair devices after use.
  • Use 2FA and a VPN on linked accounts/connections.

Mobile Phone Hacking

Endpoint
Mobile phone hacking is unauthorized access to a phone that puts the owner's identity and privacy at risk — from stolen credentials to surveillance and financial fraud.

Warning signs

  • Fast battery drain — hidden processes running.
  • Slowness / overheating — resource abuse.
  • Strange account activity — logins you didn't make.
  • Unfamiliar calls / texts — sent or received without you.

Protection

  • No sketchy apps from unknown sources.
  • Don't jailbreak / root (removes built-in protections).
  • Keep the phone with you physically.
  • Use a passcode + complex passwords.
  • No stored passwords — use a password manager.
  • Clear history/cache regularly; enable lost-device tracking.
  • Keep apps/OS updated; enable 2FA.
  • Avoid SMS/email 2FA (SIM-swap risk); use app/ hardware 2FA.
  • No public Wi-Fi without a VPN.

Session Hijacking

Module 4 · Web/App

Once a user logs in, the server tracks them with a session token (cookie). Session hijacking is stealing or forging that token to impersonate the victim — no password needed.

MethodHowDefense
Session sniffingCapture token on plaintext trafficHTTPS everywhere
Predictable session IDGuess/brute the sequential IDLong random IDs
MITMProxy the session (see Module 3)HSTS, cert pinning
XSS cookie theftScript reads document.cookieHttpOnly + Secure flags, CSP

Hardening: bind the session to IP/user-agent, set short idle timeouts, and regenerate the session ID on login and on privilege change so a stolen pre-auth token is useless.

Secure Web-Server Hardening

Checklist

Config

  • Disable directory listing & default pages
  • Remove unused modules; least privilege
  • Custom error pages (no version leaks)
  • TLS 1.2+; HSTS; strong ciphers

App & ops

  • Parameterized queries (no SQLi)
  • Output encoding + CSP (no XSS)
  • Patch framework & deps (OWASP A06)
  • WAF in front; log & monitor

The CSIRT & Perimeter Defense-in-Depth

Org view

A CSIRT (Computer Security Incident Response Team) owns detection → response. Roles: incident lead, technical responders, comms, legal. The perimeter is layered: edge firewall → IDS/IPS → internal segmentation → host controls → logging/SIEM, so no single control is the only thing standing.

Honeypots earn their place here: they sit outside production, distract attackers, and feed the SIEM real attacker TTPs with almost no false positives.
