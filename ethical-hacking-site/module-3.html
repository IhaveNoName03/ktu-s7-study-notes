Vulnerability Data Resources

Where flaws are tracked
A vulnerability is a weakness that lets an attacker enter and harm a system — a flaw in design or a misconfiguration. To exploit it, the attacker needs a tool or technique that connects to that weakness. The top sources used to trace new vulnerabilities:

1NVD

US-government repository of standards-based vulnerability data using SCAP. Enables automation of vuln management, measurement and compliance; includes checklists, flaws, misconfigurations, product names, impact metrics.

2CVE

International, free dictionary of publicly-known vulnerabilities & exposures. Common identifiers let security products exchange data. Scanning tools use CVEs for classification; SIEMs understand them.

3CERT Notes

CERT Knowledgebase — public Vulnerability Notes Database plus restricted components. Notes include summaries, technical details, remediation, affected vendors.

4VulnDB

Risk-Based Security's commercial feed — 2000+ tracked libraries, RESTful API, email alerting, CVE mapping, VTEM metrics, links to patches/exploits.

5DISA IAVA / STIG

US Defense mapping of CVE IDs to IAVAs; posted on DISA's public STIG site. A must for .gov/.mil work.

6Security Tracker

Third-party DB updated daily; focuses on non-OS flaws (infrastructure & IoT front page most).

7OVAL

Open community standard to assess & report machine state — encode system details, express states, report results; enables interoperable, reproducible metrics.

8National Council of ISACs

Sector-specific Information Sharing & Analysis Centers (MS-ISAC, FS-ISAC, A-ISAC, AUTO-ISAC, ONG-ISAC, NH-ISAC, IT-ISAC) that rapidly share threat alerts between govt and industry.

9Exploit-DB

An archive of exploits for public security — useful for finding weaknesses in your network and staying current on attacks elsewhere (see §02).

An exploit is a program or piece of code that finds and takes advantage of a flaw — it is not malware itself, but the method used to deliver malware. Defenses: EDR, threat-defense software, pen-testing programs.

KKnown exploits

Once known, the flaw is usually patched and the info goes to security vendors. Public vulns get an ID, description and references.

0Zero-day exploits

03

Network Sniffing

Listening on the wire

Sniffing monitors and records all packets crossing a network. Admins use it to troubleshoot; attackers use it to capture passwords and account info. A packet sniffer in promiscuous mode gathers all traffic. Can be active (spikes traffic into a switch LAN to monitor) or passive (no interaction; sits on a hub, needs only a LAN account).

Types of network sniffers

MAC sniffers

Sniff data relevant to a MAC-address filter.

Protocol sniffers

Sniff for specific network protocols.

LAN sniffers

Inspect an entire range of internal IP addresses.

IP sniffers

Capture all data for a specific IP filter; logged in human-readable form.

ARP sniffers

Map IP→MAC, enabling packet spoofing / poisoning attacks.

Password sniffers

Harvest credentials from traffic; hits sites without SSL/TLS encryption.

Popular tools: Wireshark, TCPdump, Microsoft Message Analyzer, EtherApe, NetworkMiner. Can capture visited sites, page contents, emails, downloaded files.
04

Man-in-the-Middle (MITM) Attacks

Intercepting traffic

An attacker eavesdrops on (or alters) communication between two legit hosts. Types of MITM:

RRogue Access Point

Attacker sets up an AP with the strongest signal; nearby devices auto-join. All victim traffic is then manipulable — no need to be on a trusted network, just close by.

AARP Spoofing

ARP resolves IP→MAC on a LAN. Attacker answers ARP requests with its own MAC, poisoning both router and workstation caches, sitting silently in the middle. Detect with arp -a (two IPs, same MAC). Prevent with VPN, static ARP, packet filtering.

mmDNS Spoofing

Multicast DNS on a LAN; attacker replies to tv.local-style requests with a fake address it controls; victim caches it as trusted.

DDNS Spoofing

Corrupt DNS cache so the victim sends sensitive data to a malicious host believing it is trusted (e.g. onlinebanking.com). Prevent with DNSSEC, source auth, rate limiting, DNS filtering, monitoring.

05

Denial-of-Service & Remote Attacks

Availability

DDoS vs DDoS

DoS uses a single computer to overwhelm a target. DDoS comes from many distributed sources (e.g. a botnet). Goal: oversaturate capacity so legitimate requests are denied.

FAttack categories

  • Buffer overflow — writing past a buffer's bounds corrupts adjacent memory, crashing the service or enabling code execution (a crash bug, not resource exhaustion).
  • Flood attacks — saturate with packets (needs more bandwidth than target).
  • Smurf / Ping flood / Ping of Death — historic ICMP-based attacks.

RRemote attacks

Target a computer/network the attacker is not using. Classified by method: DNS Poisoning, TCP Desynchronization, DoS, ICMP attacks, Port Scanning. Often start with network service scanning for unpatched software; RDP is a common target (credentials left in memory).

MMitigation

  • Network segmentation, firewalls, IDS/IPS.
  • Bandwidth limiting, CDN, anti-malware, regular scans & patching.
  • ISP / scrubbing-center DDoS mitigation.

Brute Force & Protocol Attacks

Credential & app layer

BBrute Force types

  • Simple — manual guessing of weak/custom passwords (no software).
  • Dictionary — run words (+symbols/numbers) against a username.
  • Hybrid — dictionary + simple brute force (e.g. SanDiego123).
  • Reverse — start with a known password, hunt matching usernames.
  • Credential stuffing — stolen creds replayed across sites (password reuse).

SAttacking SMTP

Abusing Simple Mail Transfer Protocol lets an attacker send spam/phishing as the victim's domain (reputation damage, blocklisting) and even enable DoS. Enabled by phishing/malware, lost devices, lack of encryption — mitigated with SSL/TLS and user education.

QSQL Server Attacks / SQL Injection

SQLi arises when user input is concatenated into a query without constraint/sanitization. Any user-controlled parameter (GET/POST params, user-agent, cookies, host) may hide a flaw. An attacker crafts SQL to read the DB schema and steal data. (Full SQLi types — In-band Error/Union, Inferential Blind Boolean/Time-based, Out-of-band — are covered on the Module 4 · Web server/SQLi page.) Entry point + exploit are both required.

Vulnerability Management Lifecycle

Operational

Finding a CVE is not the end. The lifecycle: discover assets → scan for known issues → prioritize by CVSS score × exposure → remediate (patch/compensate) → verify the fix → report. CVSS ranges: 0.1–3.9 low, 4.0–6.9 medium, 7.0–8.9 high, 9.0–10 critical.

Exploit-DB is read two ways: defenders check whether a public exploit exists for their stack (patch first); attackers use it as a ready toolkit. Either way, "known + unpatched" is the danger zone.

09

DHCP Spoofing & DNS Manipulation

Module 3

A rogue DHCP server on the network hands clients an attacker-chosen gateway and DNS, so the victim's traffic is routed through the attacker (classic MITM). Combined with DNS spoofing, the attacker can map legitimate names (e.g. bank.com) to a fake IP.

Defense

  • DHCP Snooping — switch marks trusted ports; only the real server may answer DHCP.
  • Dynamic ARP Inspection — validates ARP against the DHCP binding table.
  • DNSSEC — cryptographically signed answers foil spoofed records.
  • 802.1X port authentication stops rogue devices joining in the first place.
Attack chain recap: rogue DHCP → bad default gateway/DNS → victim traffic intercepted → DNS hijack to fake sites → credential theft over "HTTP".
E1

Vulnerability Data Sources in Depth

Deep dive · intelligence

A vulnerability is a weakness in design, implementation, or configuration that allows an attacker to harm a system. A CVE is not a database of details but a dictionary of identifiers: a number such as CVE-2023-12345 gives every vendor, scanner, and report a common name for one specific flaw. The NVD enriches those identifiers with descriptions, affected products, reference links, and CVSS scores, using the SCAP family of standards so that tools can exchange data automatically. CWE classifies the type of weakness, such as CWE-89 for SQL injection, while CPE names the exact affected product version. Together they let a scanner say "this host running product X has weakness type Y, which is CVE-Z."

Other sources serve different needs. CERT vulnerability notes provide readable summaries and remediation advice from a trusted research team. VulnDB and commercial feeds offer structured data with APIs and alerting, including libraries that public feeds may miss. DISA IAVA and STIG documents map vulnerabilities to US defence systems and provide hardening benchmarks. OVAL defines machine-readable statements that test whether a host is in a vulnerable state, which makes compliance checks reproducible. ISACs share sector-specific warnings between government and industry. Exploit-DB archives working exploit code, which is useful to defenders who need to know whether a flaw is trivially exploitable and to attackers looking for a ready-made tool.

The practical skill is to trace a scanner alert back to authoritative data. Given a CVE identifier, look up the affected versions, check whether a patch exists, read the CVSS vector to understand why the score is high, and search for public exploits to gauge urgency. Then compare with your own asset inventory: a critical CVE on a library that your application does not actually call is less urgent than a medium CVE on an internet-facing login page. This is the difference between counting vulnerabilities and managing them.

Exam tip: When asked where vulnerability information comes from, list at least four sources and say what each adds. A list of names without functions is a weak answer; a sentence explaining that CVE names, CWE classifies, NVD scores, and ISACs distribute context is a strong one.
E2

CVSS and Risk-Based Prioritisation

Deep dive · scoring

CVSS (Common Vulnerability Scoring System) produces a 0-to-10 score from a standard vector. The base metrics describe intrinsic properties: attack vector (network, adjacent, local, physical), attack complexity, privileges required, user interaction, scope, and the impact on confidentiality, integrity, and availability. Temporal metrics refine the score with exploit maturity and remediation level. Environmental metrics adjust it to a particular organisation's asset importance and controls. A number without its vector is hard to interpret; a vector tells you exactly why the number is what it is.

The bands are low (0.1–3.9), medium (4.0–6.9), high (7.0–8.9), and critical (9.0–10.0). Scores help, but they are not the whole risk. A critical remote-code-execution flaw in a lab tool with no network exposure may be a low organisational priority, while a medium flaw in the public authentication path may be urgent. Mature programmes add exploit prediction data, asset criticality, and exposure: is the system internet-facing, does it hold regulated data, and is a public exploit already in use?

Worked vector, read piece by piece

CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H  = 9.8 CRITICAL

  AV:N  exploitable over the network (no physical access needed)
  AC:L  low complexity, no special conditions
  PR:N  no privileges required
  UI:N  no user interaction required
  S:U   scope unchanged (impact stays in the vulnerable component)
  C:H/I:H/A:H  total loss of confidentiality, integrity and availability

E3

Exploits, Zero-Days, and Disclosure

Deep dive · lifecycle

An exploit is code or a technique that takes advantage of a vulnerability. It is not the same as malware: exploit code may simply demonstrate that a flaw exists, while malware is a payload delivered by an exploit. The lifecycle usually runs: a flaw is introduced, discovered by a researcher or attacker, reported to the vendor, patched, published as a CVE, and finally scanned for and exploited in the wild. The window between publication and patch deployment is the most dangerous period for defenders, because attackers have precise knowledge while many systems are still unpatched.

A zero-day is a vulnerability that is unknown to the vendor and for which no patch exists, or a weaponised exploit used before the vendor knows. Because no signature or patch is available, defences must rely on behaviour: sandboxing, least privilege, segmentation, and anomaly detection. Zero-days are expensive and rare, so most real intrusions use known flaws that someone failed to patch. This is an important exam point: advanced malware is less common than ordinary unpatched software.

Responsible disclosure means reporting a flaw privately to the vendor, allowing a reasonable time for a fix, and then publishing details so defenders can act. Full disclosure publishes immediately, which pressures vendors but also arms attackers. The ethical position expected of a white hat is to follow the agreed disclosure policy in the engagement and to avoid public release that puts users at risk. Staying within scope and documenting everything remain the dividing line between research and unauthorised access.

The slope of the curve between publication and patch deployment is where most damage occurs. Reducing that interval is the main goal of vulnerability management.

E4

Sniffing Mechanics and Filters

Deep dive · capture

A sniffer puts a network interface into promiscuous mode so that the operating system receives every frame on the segment, not only frames addressed to that host. On a hub this reveals all traffic automatically, because a hub repeats every frame out of every port. On a switch, traffic is directed to the intended port, so an attacker must use ARP poisoning, MAC flooding, a rogue access point, or a monitor/span port to observe it. Wireless networks in monitor mode similarly capture frames from the air, but encrypted WPA2/WPA3 traffic is not readable without the key.

Capture tools accept a filter expression that limits what is recorded. A capture filter such as tcp port 23 or host 10.0.0.5 is applied before storage and reduces volume. A display filter such as http.request.method == "POST" hides captured packets from view without discarding them. Knowing the difference matters operationally: capture filters save disk and CPU, display filters support later analysis. Common plaintext protocols that reveal credentials include HTTP, FTP, Telnet, and legacy SNMP; SMTP and POP3 without TLS expose mail content.

The defender's answer is not "stop using sniffers" — administrators need them — but "make captured traffic useless." TLS everywhere, SSH instead of Telnet, SFTP instead of FTP, and VPNs on untrusted networks remove readable secrets. Switched networking and port security reduce the ability to observe other hosts' frames. Monitoring for interfaces in promiscuous mode and for unexpected ARP activity catches the attacker who tries to bypass the switch.

E5

ARP Spoofing and Man-in-the-Middle Mechanics

Deep dive · interception

ARP resolves an IPv4 address to a hardware (MAC) address on a local network. A host that wants to send a packet to the gateway broadcasts "who has 192.168.1.1?" and trusts the reply. The protocol has no authentication, so an attacker can reply first with their own MAC address. If the attacker also sends a forged reply to the gateway claiming to be the victim, both sides update their ARP caches and the attacker sits in the middle of the conversation, forwarding traffic so that neither party notices.

The step-by-step attack is: identify the gateway and victim addresses, send crafted ARP replies to poison both caches, enable IP forwarding on the attacker machine, and start capturing or modifying the traffic. Detection is possible because one MAC address — the attacker's — appears against two or more IP addresses in the ARP cache (the gateway IP and another host both resolving to it), because a known IP's MAC suddenly changes, or because an IDS flags unsolicited gratuitous ARP replies. Tools that perform the attack are easy to obtain, which is why the defence must be built into the network rather than left to users.

The strongest defences are DHCP snooping, which builds a trusted binding table of MAC-to-IP assignments, and dynamic ARP inspection, which validates ARP replies against that table and drops forged ones. Static ARP entries work on small networks but do not scale. VPNs protect traffic even if an attacker succeeds in intercepting it, and TLS with certificate validation prevents silent modification. Note that these defences are diverse: one prevents the poisoning, another protects the data, and a third detects the attempt.

E6

DNS, mDNS, and Rogue DHCP Attacks

Deep dive · name and address

DNS translates names into addresses, and both the request and the reply are normally sent in a single UDP datagram. Classic DNS cache poisoning injects a false mapping into a resolver's cache so that users who type a legitimate name are silently sent to an attacker-controlled address. Historically, attackers improved their odds by guessing the 16-bit transaction ID and source port; randomised ports and IDs make brute forcing far slower. DNSSEC signs records with a chain of trust, so a resolver can verify that an answer really came from the zone owner and was not altered.

mDNS performs similar resolution on a local network using multicast, with names such as printer.local. Because it is designed for convenience, devices tend to trust the first answer they receive; an attacker on the same LAN can answer with their own address. Rogue DHCP is broader: an unauthorised DHCP server hands clients an attacker-chosen default gateway and DNS server, so every connection passes through the attacker without needing to poison ARP at all. The result is a local network where the attacker controls both the path and the names.

A complete attack chain reads: rogue DHCP supplies a malicious gateway and DNS; the victim resolves bank.example to the attacker's address; the attacker presents a cloned site with a valid-looking name; credentials are collected over a connection the attacker can read. Defences are structural: DHCP snooping limits which switch ports may answer DHCP requests, dynamic ARP inspection prevents forged mappings, DNSSEC validates answers, 802.1X stops unauthorised devices from joining, and certificate validation stops a cloned site from being accepted without a warning.

Exam tip: The most complete answer to "how do you prevent DNS spoofing?" combines cryptographic validation (DNSSEC), local controls (DHCP snooping and ARP inspection when DHCP-based), and user-side validation (HTTPS certificates). No single control covers all variants.
E7

SSL Stripping and the Rogue Access Point

Deep dive · wireless/transport

A rogue access point is an unauthorised wireless access point, often configured with the same network name as a legitimate one and a stronger signal. Clients that auto-join open or weakly configured networks connect to the attacker, who then controls their path to the internet. An evil twin is the targeted version of the same idea. Defences include wireless intrusion prevention, 802.1X authentication with a RADIUS server so clients verify the network, disabling auto-join, and keeping devices' Wi-Fi radios off when unused.

SSL stripping is a downgrade attack. The attacker establishes an HTTPS connection to the real server but serves plain HTTP to the victim, so the victim's browser shows an unencrypted session while the attacker relays everything in the clear. The classic tool rewrites https:// links to http:// and strips the secure flag from cookies. Modern defences are strong: HSTS instructs the browser to use HTTPS only for a period, the HSTS preload list hard-codes major sites, browsers warn on insecure forms, and certificate validation fails if the attacker presents a false certificate. An attacker who tries to substitute a self-signed certificate triggers a prominent warning.

Both attacks exploit convenience. Users want networks that connect automatically and pages that load without warnings; the attacker trades on that. The exam answer should therefore combine a technical control with a behaviour change: HSTS and 802.1X on the technical side, and "do not ignore certificate warnings or join unknown networks" on the human side.

  Victim  -- http://bank -->  Attacker  -- https://bank -->  Bank
          <-- plain page ----           <-- encrypted -------

  The bank believes it is talking securely to the attacker.
  The victim believes they are talking directly to the bank.

Exam tip: Distinguish sniffing from stripping: sniffing reads traffic that is already plaintext; stripping causes traffic to be plaintext. The defences overlap but the mechanism is different.
E8

Denial of Service and Remote Attacks in Depth

Deep dive · availability

Denial-of-service attacks come in two broad flavours with different mechanisms. A resource-exhaustion attack floods bandwidth, connection tables, CPU, or memory. A crash attack sends malformed input that triggers a bug — a buffer overflow, a null dereference, or a protocol parser error — and stops the service entirely. The classic examples are the SYN flood, which fills the half-open connection backlog; the Smurf attack, which spoofs a broadcast ICMP request so many hosts reply to one victim; the ping of death, which sends oversized packets to a buggy stack; and Slowloris, which opens many connections and sends headers so slowly that server threads stay occupied.

Remote attacks target a system the attacker is not physically using. They often begin by scanning for an exposed service with a known flaw, then sending a crafted request to exploit it. Remote Desktop Protocol is a frequent target because it is exposed for convenience and may be protected only by a password; credentials left in memory or weak lockout policy make it vulnerable. A successful remote attack can install a backdoor, create an account, or pivot to other machines on the internal network.

Defence combines prevention (patching, disabling unused services, strong authentication), absorption (CDN, anycast, extra capacity), and filtering (firewall thresholds, SYN cookies, upstream scrubbing). An incident plan matters because DDoS is noisy and time-critical; the team needs to know who contacts the provider and what traffic can be sacrificed. After the attack, logs and flow data help distinguish the flood from ordinary spikes.

E9

Brute Force and Credential Attacks in Depth

Deep dive · passwords

A brute-force attack tries many candidate passwords until one works. A dictionary attack tries a wordlist, often with rules that add digits and symbols. A hybrid attack combines dictionary words with common patterns such as a trailing year. A reverse brute-force starts with a known password and tries many usernames. Credential stuffing replays username-password pairs leaked from another site, relying on password reuse. Password spraying tries one common password against many accounts, which avoids lockout thresholds that are set per account.

Whether an attack can be run quickly depends on how passwords are stored. Systems should never store plaintext passwords; they store a salted hash. A salt is a random value added before hashing, so identical passwords produce different hashes and precomputed rainbow tables become useless. A deliberately slow password-hashing function such as bcrypt, scrypt, or Argon2 makes each guess expensive, which raises the cost of offline cracking. Attackers counter with GPUs and specialised hardware, so the defender must also choose a high work factor and protect the hash store.

Defence is layered. Strong password policy favours length over arbitrary complexity and screens against known-breached passwords. Multi-factor authentication makes a correct password insufficient. Rate limiting, progressive delays, and account lockout slow online guessing, but lockout must be balanced against denial of service — an attacker can deliberately lock out users. Monitoring for many failures from one source, for logins from unusual locations, and for many accounts sharing one password catches credential stuffing. Users should be taught to use a password manager and unique passwords.

Worked estimate

Assume a 4-character numeric PIN: 10,000 possibilities.
At 100 guesses/second with no lockout: 10,000 / 100 = 100 seconds.
At 1 guess/second with a 5-attempt lockout: hours per account.

Assume a 12-word passphrase drawn from a 2,000-word list:
2,000^12 possibilities -- astronomically beyond brute force.

Conclusion: length plus rate limiting defeats online guessing;
MFA is still required because offline cracking and reuse remain.
Exam tip: Name the storage control when discussing offline cracking: "salted, slow hashes" is the phrase markers look for. For online guessing, the answer is rate limiting, lockout, and MFA.
E10

Protocol Attacks: SMTP Abuse and SQL Injection

Deep dive · application

SMTP abuse occurs when an attacker uses a mail server to send messages as the organisation. An open relay accepts mail from anyone and forwards it to anyone, which is quickly abused for spam and phishing; the result is reputation damage and blocklisting. Spoofing forges the From address, so a message appears to come from a trusted colleague or brand. Three email-authentication mechanisms reduce this: SPF publishes which servers may send for a domain, DKIM adds a cryptographic signature to messages, and DMARC tells receivers how to handle messages that fail those checks and sends reports to the domain owner.

SQL injection happens when user input is concatenated into a SQL query without validation or parameterisation. If an application builds SELECT * FROM users WHERE name = '" + input + "', an attacker can supply input that closes the string and adds another condition, causing the database to return unintended rows or execute additional statements. The root cause is treating data as code. The fix is a parameterised query (prepared statement), in which the SQL structure is fixed and user values are bound separately so they can never be interpreted as SQL.

The impact includes dumping credentials, bypassing authentication, reading other users' data, modifying records, and in some configurations executing operating-system commands. Defences include parameterised queries, least-privilege database accounts, input validation as a secondary control, stored procedures where appropriate, hiding detailed database errors, and a web application firewall as a temporary compensating measure. Note that escaping input alone is fragile; parameterisation removes the possibility rather than trying to filter it.

Fig · Injection versus parameterisation
  VULNERABLE construction:
    query = "SELECT * FROM users WHERE id = '" + input + "'"
    input = "1' OR '1'='1"  ->  SELECT ... WHERE id = '1' OR '1'='1'
    result: every row returned

  SAFE construction:
    query = "SELECT * FROM users WHERE id = ?"
    bind(1, input)          ->  the database treats input strictly as a value
    result: one row, or none; the quote characters have no special power

The difference is not that the safe version "filters bad characters" — it is that user input is never allowed to become part of the query structure.

Exam tip: The single best defence for SQL injection is a parameterised query. Write that first, then add least privilege and generic errors. Avoid "escape all input" as the primary answer; it is incomplete.

Vulnerability Management as a Programme

Deep dive · operations

Finding vulnerabilities is trivial compared with fixing them in a large estate. A management programme begins with a complete asset inventory; you cannot patch what you do not know you own. Next comes discovery through authenticated scans, which see far more than unauthenticated ones, and triage using CVSS plus exposure and asset value. Remediation follows: patch, change configuration, or apply a compensating control. Verification rescans to prove the fix worked, and reporting tracks trends so management can see whether the programme is improving.

Timeframes are usually set by severity: critical issues within days, high within a couple of weeks, medium within a month or two, and low in the normal patch cycle. Exceptions must be documented with a reason, an owner, a compensating control, and an expiry date; an exception without an expiry becomes permanent. Metrics should measure outcomes such as mean time to remediate and the percentage of critical issues overdue, not just the number of scans run. A scanner that runs daily but whose findings are never fixed adds no security.

Detection Matrix and Exam Guidance

Consolidation

Bring the attacks of this module together with the evidence they leave. Sniffing leaves a promiscuous interface or unexpected capture traffic. ARP poisoning leaves duplicate MAC mappings. DNS spoofing leaves a name resolving to an unexpected address. SSL stripping leaves HTTP where HTTPS is expected. DoS leaves anomalous traffic volume, connection counts, or CPU load. Brute force leaves repeated authentication failures. SQL injection leaves unusual query strings in web logs and database errors. Each of these can feed a SIEM rule, and each illustrates the same principle: attacks are processes, and processes create traces.

What to write for 3 marks and for 14 marks

Three marks: state three precise points. For "what is a zero-day?", write: it is a vulnerability unknown to the vendor; no patch exists; defenders must rely on behaviour-based detection and layered controls. Fourteen marks: define the terms, build a taxonomy in a table, give a worked example with a command or vector, show the attack mechanism, give detection indicators, give defences at more than one layer, and conclude with an evaluation. For instance, a question on man-in-the-middle attacks can cover ARP, DNS, DHCP, rogue access points, and SSL stripping, then compare detection and prevention for each.

Module glossary

Vulnerability — a weakness. Exploit — a method that abuses it. Zero-day — an unpatched, unknown flaw. Promiscuous mode — accepting all frames. MITM — secretly relaying or altering a conversation. Amplification — multiplying traffic with spoofed requests. Salting — adding random data before hashing passwords. Parameterised query — SQL with values bound separately. Residual risk — exposure remaining after controls.

Exam tip: Finish every attack answer with the defender's perspective. "Every attack leaves an indicator" is a reliable closing sentence, but name at least one indicator to prove it.
