Routers

Infrastructure
A router is a networking device that connects two or more packet-switched networks and forwards data packets between them, choosing the best path toward the destination.

F Core Functions

  • Packet forwarding — switch packets from ingress to the correct egress interface.
  • NAT (Network Address Translation) — rewrite source/destination addresses, sharing one public IP across a private range.
  • Packet filtering / ACLs — permit or deny traffic by rule (address, port, protocol).
  • Interconnecting technologies — link Ethernet, serial, fiber, wireless segments.
  • Path selection — pick the "best" route to a destination.
  • Dynamic routing — learn routes via OSPF (interior) and BGP (inter-AS).
  • QoS — prioritize latency-sensitive traffic (voice/video).
  • VLAN segmentation and acting as a DHCP server.

A Architecture

  • Input interface — receives packets, performs MAC/CRC check, looks up the forwarding table.
  • Routing processor (control plane) — runs routing protocols, maintains the routing/forwarding table, enforces ACLs.
  • Output interface — queues and transmits packets toward the next hop, applying QoS/shaping.

In high-end routers the data plane (forwarding) is often hardware-accelerated while the routing processor handles the control plane.

S Security Challenges

  • Firmware vulnerabilities — embedded code flaws; patch regularly via vendor updates.
  • DDoS on infrastructure — volumetric / protocol attacks saturate the router, blackholing legitimate traffic.
  • Default admin credentials — shipped admin/admin logins left unchanged give full takeover; change them and disable remote management.

Firewall

Perimeter
A firewall is a network security system that monitors and filters incoming/outgoing traffic according to a security policy — acting as a barrier between an internal (trusted) network and an untrusted network such as the internet.

Firewall Generations

1 Gen 1 — Virus

1980s. Threat was the computer virus; the response was antivirus software scanning files/signatures.

2 Gen 2 — Network

Mid-1990s. Threat moved to the network; the firewall was born to filter traffic at the perimeter.

3 Gen 3 — Application

2000s. Application-layer attacks drove IPS (Intrusion Prevention Systems) to inspect/block at L7.

4 Gen 4 — Payload

~2010. Targeted payloads & bots; defense added anti-bot and sandboxing to detonate unknown files.

5 Gen 5 — Mega

~2017. Large-scale, multi-vector "mega" attacks; advanced threat prevention (AI/threat-intel) is required.

+ NGFW

Next-Gen Firewall = the culmination: deep packet inspection + application-level control, and it integrates IPS inline.

Firewall Types

Packet Filtering

Stateless inspection of packets against ACLs (source/dest IP, port, protocol). Fast, cheap, but blind to connection state.

Proxy Service (Application-Layer)

Acts as an intermediary; the client talks to the proxy, the proxy fetches on its behalf. Full L7 visibility, can filter content, but slower.

Stateful Inspection

Tracks the state of active connections (state table) and makes decisions based on context — not just individual packets.

NGFW (Next-Gen Firewall)

Adds deep packet inspection and application-level awareness (user/app identity, threat feeds). A true NGFW integrates IPS.

Honeypots

Deception
A honeypot is a security resource whose value lies in being probed, attacked, or compromised — a decoy system that lures, deflects, and studies attackers while appearing to be a high-value asset (database, server, router).

Placement

  • DMZ — exposed segment between firewall and internet; common, realistic exposure.
  • Outside the firewall — to study raw internet attack traffic with no filtering.

Scale-out terms

  • Honeynet — a network of two or more honeypots working together.
  • Honey farm — a centralized collection of honeypots managed from one place.

Types

Production vs Research

Production honeypots protect an organization (added risk detection). Research honeypots gather threat intelligence (used by vendors/analysts).

Pure / High-Interaction

A full real system with real services and often root access to the attacker. More realistic data but riskier — a compromise can be used to pivot.

Low-Interaction

Simulates common attack vectors only (e.g. Honeyd). Safe, cheap, easy to deploy; great for detecting bots/automated malware but gives less depth.

Specialized Honeypots

Malware honeypot

Collects and analyzes malware binaries.

Spam honeypot

Traps spam/abuse (open relays, spam sinks).

Database honeypot

Decoy DB to catch SQL injection/data theft.

Client honeypot

Proactively seeks out malicious servers (drives a client to detect drive-by attacks).

Benefits & Disadvantages

Benefits

  • Real data — captures actual attacker behavior.
  • Fewer false positives — any interaction is by definition suspicious.
  • Cost-effective — cheap relative to full IDS tuning.
  • Encryption circumvention — attackers decrypt/operate in clear once inside the decoy.

Disadvantages

  • Limited data — only sees what hits the honeypot.
  • Isolated — no view of the full enterprise.
  • Distinguishable — skilled attackers may detect the decoy.
  • Can risk production — a high-interaction compromise can be used to pivot into real systems.

IDS vs IPS

Detection / Prevention
IDS (Intrusion Detection System) is passive: it watches traffic, detects suspicious activity and raises an alert — it does not block. IPS (Intrusion Prevention System) sits inline in the traffic path and can block or stop malicious traffic in real time.
DimensionIDS (Detection)IPS (Prevention)
PositionOut-of-band (span/monitor port)Inline (must see & forward traffic)
ActionAlert / log onlyBlock / drop / reset connection
Latency impactNone (passive)Adds processing latency (inline)
Risk if it failsMisses detectionCan become a bottleneck / single point of failure
Best forVisibility, forensics, complianceActive blocking of known/likely attacks

IDS Classifications

By placement / scope

  • NIDS — Network-based; watches network segments.
  • HIDS — Host-based; watches a single host (files, logs, syscalls).
  • PIDS — Protocol-based; monitors a protocol/interface.
  • APIDS — Application-specific; watches app-layer (e.g. DB queries).
  • Hybrid — combines multiple sensors / correlation.

By detection method

  • Signature-based — matches known attack patterns (like AV signatures); fast but blind to new attacks.
  • Anomaly-based — flags deviations from a learned "normal" baseline; can catch novel attacks but more false positives.

IPS Classifications

By placement

  • NIPS — Network IPS (inline at a network point).
  • WIPS — Wireless IPS (monitors/blocks rogue APs & wireless attacks).
  • HIPS — Host IPS (blocks on the endpoint).

By technique

  • NBA (Network Behavior Analysis) — watches traffic for anomalous behavior across the network.
  • Signature, statistical-anomaly, and stateful protocol analysis (validates protocol-state conformance) are the three common analysis methods, shared with IDS concepts.

Web Filtering

Content Control
Web filtering is the practice of controlling which web resources users may reach — it can allow or block content by category, domain, or policy.

Allow-list vs Block-list

  • Allow-list (whitelist) — only explicitly approved sites are reachable; maximum security, low usability.
  • Block-list (blacklist) — everything allowed except known-bad sites; higher usability, gaps remain.

Filtering techniques

  • DNS filtering — resolve or sinkhole domains at the DNS layer.
  • URL filtering — match the requested URL/path against categories or patterns.
  • Content filtering — inspect page content (keywords, MIME, policies).

Server-side vs Client-side

  • Server-side — enforced at a proxy/gateway (central, harder to bypass).
  • Client-side — enforced on the endpoint (browser/agent); easier for users to tamper with.

Why filter the web?

  • Malware protection — block drive-by / exploit sites.
  • Data security — stop exfiltration to webmail/cloud.
  • Compliance — meet regulatory / acceptable-use rules.
  • Policy — enforce acceptable-use and productivity rules.

Web Server

Application
A web server is the hardware + software that stores, processes and delivers web content using the HTTP/HTTPS protocol.

Request flow (how a page loads)

  1. User enters a URL in the browser.
  2. Browser performs a DNS lookup to resolve the domain to an IP.
  3. Browser sends an HTTP request to the server (e.g. GET /index.html).
  4. Server processes it and returns an HTTP response (status + headers + body).
  5. Browser renders the content.

Static vs Dynamic content

  • Static — pre-built files served as-is (HTML, CSS, images).
  • Dynamic — generated on the fly by server-side code (e.g. ASP / PHP) pulling from a database.

Common servers & capabilities

  • Apache, IIS, Nginx, Lighttpd, Sun Java System (Web Server).
  • Can also handle SMTP / FTP and other protocols.
  • Run server-side scripting via ASP, PHP, etc. to build dynamic pages.

SQL Injection (SQLi)

Web Attack
SQL injection is a code-injection technique where an attacker inserts malicious SQL into an input field so the application executes it against the backend database, manipulating queries it was never meant to run.

In-band

Attacker uses the same channel for the attack and to read results.

  • Error-based — provoke DB errors that leak schema/info.
  • Union-based — UNION a malicious SELECT to append data to the page output.

Inferential / Blind

No data returned directly; the attacker infers answers from behavior.

  • Boolean-based — true/false responses reveal bits of data.
  • Time-based — inject WAITFOR/SLEEP() delays to extract data through timing.

Out-of-band

Results are exfiltrated over a different channel than the injection:

  • DNS — trigger the DB to resolve an attacker-controlled domain carrying data.
  • HTTP — make the DB issue an outbound HTTP request to the attacker.
Impact: attackers can view secret lists (dump users/credentials), delete or alter tables, and gain admin privileges — full compromise of the data tier.

Cross-Site Scripting (XSS)

Web Attack
XSS is a web vulnerability that lets a third party execute a script in the victim's browser — usually by injecting client-side code (JavaScript) that the site then serves to other users.

Reflected XSS

The malicious payload is embedded in the request and reflected back in the response. The script runs immediately when the victim opens a crafted link (e.g. a search box that echoes input). Not stored — it needs the victim to trigger it.

Stored XSS

The payload is saved on the server (database/comment field) and served to every user who views it — e.g. a comment thread that stores <script> which executes for everyone reading the comments. More dangerous because it hits many victims passively.

Note on DOM-based XSS

Although the PDF's primary two types are Reflected and Stored, a DOM-based variant is widely recognized in practice: the payload is executed by manipulating the Document Object Model in the victim's browser (client-side logic) rather than server output. Keep it in mind for real-world testing, but treat Reflected/Stored as the core exam pair.

Exploit Writing

Offensive
Writing an exploit is the process of turning a known vulnerability into reliable, repeatable code that subverts a program's intended behavior (typically to gain control of execution).

Workflow

  • 1. Identify the vulnerability — find the bug (overflow, format string, etc.).
  • 2. Attach a debugger — run the target under a debugger to observe registers/memory at the crash.
  • 3. Overwrite the return value — craft input so the saved return address is overwritten with a controlled value (the seed of control hijack).
  • 4. Automate — script the PoC with Perl / Python for repeatable delivery.
  • 5. Find a DLL address — locate a loaded module's (DLL) address containing useful instructions (e.g. JMP ESP) to redirect execution into the injected shellcode.

Outcome

Once the return address points at attacker-controlled memory and a reliable jump is found, the injected shellcode runs with the process's privileges — giving a shell, privilege escalation, or payload execution.

Reliability concerns: bad characters, address randomization (ASLR), and stack protections must be handled.

Buffer Overflow

Memory Corruption
A buffer overflow occurs when a program writes data that exceeds the allocated buffer's capacity, causing it to overflow into adjacent memory and overwrite other data or control structures.

System crash

Overwritten data corrupts execution → the process (or OS) crashes / becomes unstable.

Access-control loss

Overwriting permission/control data can defeat the program's intended security checks.

Further exploits

The overflow becomes the foothold for injecting and running attacker shellcode.

Arbitrary code execution: by overwriting a return address or function pointer, an attacker can redirect execution to their own code — the root cause behind most classic remote exploits (and the mechanism exploited in §9).

Reverse Engineering

Analysis
Reverse engineering (RE) is the process of analyzing a product — software or hardware — to understand its functions and information flow. In security it is heavily used for malware RE (understanding what malicious code does without source).

The PDF's three "stages"

The source lists these stages (notably framed around physical scanning of an object):

  • Scanning — capture the geometry / data of the target.
  • Point Processing — clean and process the captured point data.
  • Geometric Model — reconstruct a usable model from the processed points.

⚠ These are the PDF's literal stages and are kept here for fidelity, though they describe a 3D-scanning view of RE rather than code RE.

The standard security RE view

For malware/software RE, the practical stages are:

  • Information gathering — collect binaries, strings, metadata, packer info.
  • Disassembly / decompilation — turn machine code back into assembly / higher-level code.
  • Static + dynamic analysis — read code statically and run it in a sandbox to observe runtime behavior.
  • Documentation — record findings, IoCs, and the program's logic.

Tools

Debuggers (user-mode / kernel-mode)

  • IDA Pro — disassembler + debugger (industry standard).
  • OllyDbg — popular user-mode Windows debugger.
  • GDB — GNU debugger (Linux / native).
  • Immunity Debugger — exploit-dev oriented.
  • WinDbg — Microsoft kernel/user debugger.

Other RE tooling

  • Fault Injection tools — deliberately induce errors to expose behavior.
  • Disassembler — convert binary to assembly (often IDA/Radare2/Ghidra).
  • Decompiler — reconstruct higher-level (C-like) source from binaries.

Email Hacking

Account / Comms
Email hacking is the unauthorized access to, or manipulation of, someone's email account or messages — to read, send, or alter mail without permission.

Phishing

Fake messages trick users into revealing credentials or clicking malicious links.

Password guessing

Tries likely passwords (common/known) against the account.

Brute force

Systematically tries many password combinations until one works.

Malware

Keyloggers / trojans capture credentials or sessions on the victim's device.

Session hijacking

Steals an active session token/cookie to ride an authenticated session.

MITM

Man-in-the-Middle intercepts mail traffic on an insecure network.

Email spoofing

Forging the sender address so mail appears to come from someone else — used in phishing/BEC. Defenses: SPF, DKIM, DMARC to authenticate legitimate senders.

Incident Response

Process
Incident response is the organized approach to handling a security breach — detecting, containing, and recovering — to minimize damage, cost, and recovery time. Owned by the CSIRT (Computer Security Incident Response Team).

Step 1 — Early Detection

Spot the incident early, e.g. a SIEM alert flagging anomalous activity or an IDS/IPS alarm.

Step 2 — Analysis

Investigate: collect IoC (Indicators of Compromise), triage scope and severity.

Step 3 — Prioritization

Rank by business impact and urgency to decide response order.

Step 4 — Notification

Notify internal stakeholders and, where required, external parties (customers, regulators, partners).

Step 5 — Containment & Forensics

Stop the spread (isolate systems) while preserving evidence for forensic analysis.

Step 6 — Recovery

Eradicate the threat, rebuild clean systems, restore from trusted backups, and patch the root cause.

Step 7 — Incident Review

Post-mortem: document what happened, what worked, and improve detections/processes so the same incident doesn't recur.

Bluetooth Hacking

Wireless
Bluetooth hacking means locating Bluetooth-enabled devices and exploiting weaknesses in the protocol or its configuration to attack them.

Bluesmacking

A DoS attack abusing L2CAP — flooding the device with oversized/ping packets to crash or hang it.

Bluejacking

Sending unsolicited messages (usually just text/contact cards) to a victim's device — mostly annoying, low harm.

Bluebugging

Taking control of a device left in discovery mode — making calls, reading SMS, using features without permission.

Bluesnarfing

Stealing data (e.g. SMS, contacts, calendar) from a vulnerable device over the Bluetooth link.

Prevention

  • Turn Bluetooth off when not in use.
  • Reject unknown pairing requests.
  • Update firmware/OS to fix BT flaws.
  • Keep devices non-discoverable (hidden).
  • Unpair devices after use.
  • Use 2FA and a VPN on linked accounts/connections.

Mobile Phone Hacking

Endpoint
Mobile phone hacking is unauthorized access to a phone that puts the owner's identity and privacy at risk — from stolen credentials to surveillance and financial fraud.

Warning signs

  • Fast battery drain — hidden processes running.
  • Slowness / overheating — resource abuse.
  • Strange account activity — logins you didn't make.
  • Unfamiliar calls / texts — sent or received without you.

Protection

  • No sketchy apps from unknown sources.
  • Don't jailbreak / root (removes built-in protections).
  • Keep the phone with you physically.
  • Use a passcode + complex passwords.
  • No stored passwords — use a password manager.
  • Clear history/cache regularly; enable lost-device tracking.
  • Keep apps/OS updated; enable 2FA.
  • Avoid SMS/email 2FA (SIM-swap risk); use app/ hardware 2FA.
  • No public Wi-Fi without a VPN.

The CSIRT & Perimeter Defense-in-Depth

Org view

A CSIRT (Computer Security Incident Response Team) owns detection → response. Roles: incident lead, technical responders, comms, legal. The perimeter is layered: edge firewall → IDS/IPS → internal segmentation → host controls → logging/SIEM, so no single control is the only thing standing.

Honeypots earn their place here: they sit outside production, distract attackers, and feed the SIEM real attacker TTPs with almost no false positives.
E1

Router Architecture and Hardening

Deep dive · infrastructure

A router connects networks at layer 3 and forwards packets toward their destination. It is useful to separate its two planes. The control plane runs routing protocols such as OSPF and BGP, builds the routing table, and manages interfaces and ACLs; it is essentially a small computer running an operating system. The data plane takes an arriving packet, looks up the best next hop, rewrites the layer-2 header, and sends it out; on high-end devices this is done in specialised hardware. Attacks against the control plane, such as a flood of routing updates or a compromised management interface, can break the whole network even when the data plane is healthy.

Routing decision is by longest-prefix match: of all the routes whose network prefix contains the destination address, the one with the most specific mask wins. Static routes are explicit and predictable; dynamic routing adapts to change but introduces trust in neighbours. BGP, which glues autonomous systems together, historically trusted route advertisements and is vulnerable to route hijacking; protections include prefix filtering, RPKI validation, and MD5/TCP-AO authentication of sessions. NAT conserves public addresses and hides internal addressing, but it complicates logging because many internal hosts share one external IP.

Security hardening of a router follows a short checklist: change default credentials, disable unused services and interfaces, restrict management to a dedicated network with strong authentication, apply ACLs in both directions, log to an external collector, keep the firmware patched, and backups of configuration stored securely. ACLs are evaluated top-down with an implicit deny at the end, so rule order is critical. A rule that denies all traffic before the specific permit is silently useless.

ComponentFunctionRiskHardening
Control planeRouting protocols, table, managementRoute hijack, CPU exhaustionAuthentication, filtering, rate limits
Data planePacket forwardingACL mistakes, bandwidth saturationReviewed ACLs, QoS, capacity
Management interfaceConfiguration accessDefault credentials, exposed serviceMFA, jump host, out-of-band network
FirmwareEmbedded operating systemUnpatched vulnerabilitiesPatch cycle, integrity checking
Exam tip: The control-plane versus data-plane distinction is a high-value sentence in a router question. Add that a router is itself a host and must be patched, credential-hardened, and monitored like any other device.

Firewall Generations and Deployment

Deep dive · perimeter

The "generations" of firewall describe a moving threat landscape. The first response to viruses was antivirus. When attacks moved to the network, packet-filtering firewalls appeared. Application-layer attacks produced intrusion-prevention systems and proxies. Targeted payloads and bots produced sandboxing and anti-bot features. Large multi-vector campaigns produced advanced threat prevention with threat intelligence. The next-generation firewall combines stateful inspection, deep packet inspection, application identity, user identity, and inline IPS in one device.

A packet-filtering firewall checks each packet against an ACL; a stateful firewall keeps a table of connections and allows return traffic only for established sessions; a proxy terminates connections and inspects content; an NGFW adds application awareness. Deployment topology matters as much as the device. A single firewall between internet and LAN leaves no protection if it fails; a DMZ places public servers on a separate segment so a compromised web server cannot reach the internal LAN directly; an internal segmentation firewall limits lateral movement between departments.

Rules should be written with implicit deny, ordered from specific to general, and reviewed regularly. Logging should capture both permitted and denied traffic, because allowed flows are often where an incident is visible. A firewall that only blocks is half a control: it also needs to tell you what it saw.

TypeLayerTracks state?Inspects content?Best use
Packet filter3–4NoNoFast, simple boundary control
Stateful firewall3–4YesNoStandard perimeter defence
Proxy firewall7YesYesContent policy, anonymity
NGFW3–7YesYesApplication control plus inline IPS
Exam tip: For a firewall question, name the type, the layer it works at, whether it tracks state, and where it sits in the topology. Add the DMZ to show that placement is part of the design.

Honeypots in Depth

Deep dive · deception

A honeypot is a decoy whose value lies in being attacked. Because no legitimate user should touch it, any interaction is suspicious, which gives honeypots an unusually low false-positive rate. They are placed in the DMZ to look like a real public server, or outside the firewall to capture the raw traffic hitting an unfiltered host. Several honeypots form a honeynet; a centrally managed collection is a honey farm.

The central trade-off is interaction. A low-interaction honeypot emulates a few services, is cheap and safe, and is excellent at catching automated bots, but a skilled attacker notices the simulation. A high-interaction honeypot is a real system with real services and sometimes root access; it yields rich intelligence about attacker tools and behaviour but carries the risk that the attacker uses it to pivot. Production honeypots protect a specific organisation by adding detection, while research honeypots collect threat intelligence for vendors and analysts.

Specialised variants include malware honeypots that collect samples, spam honeypots that trap open relays, database honeypots that look like valuable data stores, and client honeypots that actively visit malicious servers to detect drive-by attacks. Benefits are real attacker data, few false positives, low cost relative to tuning a full IDS, and the ability to watch attackers work in the clear once they are inside. Disadvantages are limited visibility, the risk of pivot from a high-interaction decoy, and the need to isolate the honeypot so it cannot harm production.

DimensionLow interactionHigh interaction
ImplementationSimulated servicesReal operating system
RiskLowHigher — can be used to pivot
Data richnessBasic: scans, payloadsDeep: tools, behaviour, keystrokes
Best forBot and worm detectionResearch and TTP collection
MaintenanceCheap, simpleResource-intensive, needs isolation
Exam tip: The phrase "any traffic to a honeypot is suspicious by definition" explains the low false-positive rate. Pair it with the main disadvantage — limited view and possible pivot risk — for a balanced answer.
E4

IDS and IPS in Depth

Deep dive · detection

An IDS is a passive observer: it receives a copy of traffic through a span port or network tap, analyses it, and raises alerts. It cannot stop an attack directly. An IPS sits inline, so traffic must pass through it, and it can drop packets or reset connections in real time. The inline position gives power but also creates latency and a potential single point of failure; many organisations therefore use IDS for visibility and IPS only for high-confidence signatures.

Detection methods divide into signature-based, which matches known patterns and is precise but blind to novel attacks, and anomaly-based, which learns a baseline and flags deviations, catching new behaviour but producing more false positives. Stateful protocol analysis checks whether a conversation follows the expected protocol state machine. Placement gives another axis: NIDS watches network segments, HIDS watches a host's files, logs, and system calls, WIPS watches wireless, and application-specific sensors watch a single application such as a database.

Tuning is the unglamorous core of the job. Too many false positives and analysts ignore the alerts; too many false negatives and incidents go unseen. A tuning cycle reviews each rule, suppresses noise from known-safe systems, adjusts thresholds using real traffic, and measures coverage against ATT&CK techniques. Alerts should include enough context — source, destination, rule, and payload — for an analyst to decide quickly.

DimensionIDSIPS
PositionOut of band (copy of traffic)Inline (in the path)
ResponseAlert and logBlock, drop, reset
LatencyNone on production trafficAdds processing delay
Failure modeMissed detectionCan break traffic flow
Analysis methodsSignature, anomaly, statefulSame, with automated response
Exam tip: A false positive is a harmless event flagged as malicious; a false negative is a real attack that was missed. Being able to define both and say which each detection method tends to produce is a common examiner favourite.
E5

Web Filtering and Content Control

Deep dive · policy

Web filtering controls which resources users can reach. An allow-list permits only explicitly approved destinations and gives maximum security with low usability, while a block-list permits everything except known-bad destinations and is easier to use but always has gaps. Filtering can happen at the DNS layer by refusing to resolve or sinkholing a domain, at the URL layer by matching the full path against categories, or at the content layer by inspecting the returned page. Enforcement can be central at a proxy or gateway, which is harder to bypass, or local on the endpoint, which is easier to deploy but easier to tamper with.

TLS inspection extends filtering to encrypted traffic by terminating and re-signing HTTPS at the proxy. It gives visibility into hidden threats but introduces privacy concerns, certificate-management overhead, and a new high-value target. Many organisations therefore inspect selected categories only. Filtering supports malware protection, data-loss prevention, compliance with acceptable-use policy, and productivity, but it must be governed: an over-broad block list drives users to bypass it, which is worse than a narrower, well-explained policy.

URL filteringRequest pathCategory and path controlNeeds plaintext or TLS inspection
Content filteringResponse bodyInspects actual contentResource-intensive, privacy concerns

Exam tip: Compare allow-list and block-list with the security-versus-usability trade-off. Add that DNS filtering blocks an entire category early, before a connection is even made.
E6

Web Servers and the Request Lifecycle

Deep dive · application

A web server is hardware plus software that serves content over HTTP or HTTPS. When a user enters a URL, the browser resolves the name through DNS, opens a TCP connection, negotiates TLS if HTTPS is used, and sends an HTTP request such as GET /index.html HTTP/1.1 with headers describing the client and what it accepts. The server maps the path to a file or passes it to application code, which may query a database, and returns a response with a status code, headers, and a body. The browser renders the body and repeats the process for each referenced resource.

Status codes tell the story: 2xx means success, 3xx redirection, 4xx a client error such as a missing page or failed authentication, and 5xx a server-side failure. Verbose error pages that reveal framework versions are an information-disclosure risk, so custom generic errors should be configured. Static content is served from files; dynamic content is generated by PHP, ASP.NET, or another runtime. Common servers include Apache, Nginx, IIS, and Lighttpd; a single host may also provide FTP and SMTP.

Hardening covers removal of default pages and sample applications, disabling directory listing, running the service under a low-privilege account, restricting available modules, setting security headers, enforcing TLS 1.2 or newer, and patching the framework and dependencies. A reverse proxy can hide server details, terminate TLS, cache content, and absorb requests before they reach the application.

200OKBaseline success; compare lengths when testing

401 / 403Unauthorised / ForbiddenAuthentication and authorisation behaviour

Exam tip: The request lifecycle question rewards ordering: DNS, TCP, TLS, request, processing, response, rendering. Add that each step is a possible control point — DNS filtering, WAF, authentication, output encoding.
E7

SQL Injection in Depth

Deep dive · data tier

SQL injection is a code-injection flaw in which untrusted input is treated as part of a database query. Its root cause is building SQL by string concatenation. In in-band attacks the same channel carries both the input and the result: error-based injection provokes messages that reveal the schema, while union-based injection appends a second SELECT so its results appear in the page. In inferential or blind injection no data is returned; the attacker asks true-or-false questions and observes behaviour (boolean-based) or injects a delay with SLEEP() or WAITFOR and measures the response (time-based). In out-of-band injection the database is made to resolve a crafted DNS name or issue an HTTP request carrying the data to the attacker.

Any request parameter can be an entry point: query strings, form fields, cookies, headers, and even JSON bodies. Automated tools discover candidates by sending marker characters and watching for errors or changes in response length, then confirm with a controlled payload. The business impact ranges from reading hidden data to bypassing login, modifying records, and, with excessive database privileges, reading files or executing commands.

The definitive fix is a parameterised query, also called a prepared statement: the SQL structure is compiled first and values are bound afterwards, so a quote in the input is just a character in a value. Secondary controls are least-privilege database accounts, input validation with allow-lists, hiding detailed errors, a WAF as a temporary measure, and code review. Stored procedures and object-relational mappers help when used with parameterisation, but neither is automatically safe if raw SQL is concatenated inside them.

E8

Cross-Site Scripting in Depth

Deep dive · browser

XSS lets an attacker run JavaScript in another user's browser within the context of a trusted site. It is not the server that is compromised; the browser is, and it trusts the site's origin, so the script can read cookies, make requests as the user, or rewrite the page. In reflected XSS the payload is part of the request and echoed in the response, so the victim must open a crafted link. In stored XSS the payload is saved on the server, for example in a comment, and executed for everyone who views it, which makes it far more dangerous. A third form, DOM-based XSS, arises when client-side JavaScript writes data from the URL into the page without safe handling; the server never sees the payload.

Defence depends on context. Output encoding converts characters into safe representations for the place they are inserted — HTML body, attribute, script, or URL — and is the core control for reflected and stored XSS. A Content Security Policy restricts which scripts may execute and where they may load from, limiting the damage if a payload gets through. HttpOnly cookies cannot be read by JavaScript, which blunts session theft. Frameworks that auto-escape templates help, but developers must still avoid dangerous sinks such as innerHTML with untrusted data.

Testing should use a harmless proof such as a marker string that appears as text rather than executing, then confirm which context reflects it. Stored XSS is tested by saving the marker and revisiting the page as another user. The report should state the context, the impact, and the specific encoding needed, because the generic phrase "sanitise input" does not tell a developer what to change.

E9

Exploit Writing and Buffer Overflows

Deep dive · memory

A buffer overflow occurs when a program writes more data into a fixed-size buffer than it can hold, so the excess overwrites neighbouring memory. On the stack, a function's local variables and saved return address sit close together; a long input can overwrite the return address so that when the function finishes, execution continues wherever the attacker chooses. That is the classic path to arbitrary code execution: place shellcode in memory, point the return address at it, and the program runs the attacker's instructions with its own privileges.

The exploit-development workflow is methodical. First identify the vulnerable input and confirm the crash under a debugger. Then determine the exact offset — the number of bytes needed to reach the saved return address — often using a cyclic pattern and reading the offending value from the crash. Next find a reliable jump instruction in a loaded module, such as JMP ESP, so execution is redirected into the injected buffer. Finally place shellcode, accounting for bad characters that would break the payload, and test reliability across restarts.

Modern systems include several defences. ASLR randomises memory addresses so hardcoded jump addresses fail. DEP / NX marks stack and heap memory as non-executable so injected code will not run. Stack canaries place a known value before the return address and abort if it changes. Fortified compiler functions and safe languages eliminate many overwrite conditions. Attackers respond with information leaks to defeat ASLR and return-oriented programming to bypass DEP, but these raise the difficulty considerably.

E10

Reverse Engineering in Depth

Deep dive · analysis

Reverse engineering is the analysis of a system to recover its design and behaviour without relying on source code or documentation. In security it is used to understand malware, verify suspicious binaries, find vulnerabilities in compiled software, and develop compatible or patched versions. The process begins with information gathering: file type, hashes, strings, imports, headers, and whether the file is packed. Static analysis then reads the disassembly or decompiled code without running it. Dynamic analysis executes the sample in an isolated sandbox and observes files, registry, processes, and network traffic. Findings are documented with indicators of compromise and a description of behaviour.

Tools divide by purpose. A disassembler converts machine code to assembly; a decompiler reconstructs higher-level pseudocode; a debugger lets the analyst step through execution and inspect registers and memory. IDA Pro, Ghidra, and Radare2 are common disassemblers; OllyDbg, Immunity, WinDbg, and GDB are common debuggers. Fault-injection techniques deliberately alter execution to expose hidden behaviour. The syllabus's literal three stages — scanning, point processing, geometric model — describe reverse engineering of physical objects by 3D scanning and are retained for fidelity, but the security workflow above is the one used for software and malware.

Analysis must be done safely: a sandboxed, non-networked environment with snapshots, because malware may detect virtual machines or destroy data. Legally, reverse engineering must be authorised; examining a competitor's binary or a customer's software without permission can breach contract or law even when the motive is research.

E11

Email Security and Spoofing Defences

Deep dive · communications

Email was designed for a more trusting internet, so its basic protocols provide little proof of identity. Email hacking covers unauthorised access to an account or manipulation of messages: phishing for credentials, password guessing and brute force, keylogging malware, session theft, interception on insecure networks, and spoofing of the sender address. Business email compromise often uses no malware at all — just a convincing impersonation of an executive requesting a payment.

Three standards make forgery detectable. SPF publishes, in DNS, which servers are allowed to send for a domain; a receiver checks the connecting server's address against that list. DKIM adds a signature over selected headers and the body, verified with a public key in DNS, proving the message was not altered in transit and came from an authorised sender. DMARC ties the two together: it requires alignment between the visible From domain and the authenticated domain, and tells receivers whether to monitor, quarantine, or reject failures while sending reports back to the owner. Deployment is gradual — start in monitoring mode, fix legitimate senders, then move to rejection.

User-side controls remain essential because a compromised legitimate account passes all three checks. MFA protects the mailbox, unusual-login alerts flag takeover, and payment procedures requiring out-of-band confirmation stop the classic CEO-fraud flow. Users should inspect the real sender address rather than the display name and treat urgent secrecy as a warning sign.

E12

Incident Response in Depth

Deep dive · process

Incident response is the organised handling of a breach to limit damage and restore normal operation. A widely used six-phase model begins with preparation: building the CSIRT, playbooks, contacts, and logging before anything happens. Detection and analysis turns alerts into an incident, collects indicators of compromise, and determines scope. Containment stops the spread, ideally in two steps — short-term isolation followed by a more durable fix. Eradication removes the attacker's access, persistence, and artefacts. Recovery restores systems from trusted media, patches the root cause, and monitors for recurrence. Post-incident review records lessons and improves controls.

Evidence must be collected in order of volatility: memory and network connections first, then disk, then backups, because the most fragile data disappears first. Images and hashes preserve integrity, and a chain of custody records who handled each item. Containment decisions are a balance: pulling the network cable preserves evidence but may destroy volatile data and interrupt the business, so the playbook should say which takes precedence for each system type.

Communication is part of the technical response. Legal, public relations, regulators, and customers may all need notification within fixed deadlines. A single incident lead coordinates messages so that technical staff are not improvising public statements. After recovery, the review should produce tracked actions with owners — otherwise the same incident recurs and the effort was wasted.

E13

Bluetooth and Mobile Security in Depth

Deep dive · wireless endpoints

Bluetooth attacks exploit the short-range radio link and the tendency of devices to pair automatically. Bluejacking sends unsolicited messages and is mostly a nuisance. Bluesnarfing copies data such as contacts and messages from a vulnerable device. Bluebugging takes control of a device in discovery mode, making calls or reading messages. Bluesmacking is a denial of service that floods L2CAP packets. The common enabling conditions are discoverability, weak or absent pairing authentication, and unpatched firmware.

Mobile phone hacking targets the device as an endpoint. Warning signs include rapid battery drain, overheating, unfamiliar calls or messages, and account activity the owner does not recognise. Protection is a familiar set applied to a smaller device: install only trusted applications, avoid jailbreaking or rooting because it removes built-in sandboxing, keep the operating system updated, use a strong passcode, enable full-device encryption, use a password manager, avoid public Wi-Fi without a VPN, and choose app-based or hardware second factors rather than SMS because SIM-swap attacks can intercept codes.

At organisational level, mobile device management enforces passcode policy, remote wipe, application allow-lists, and encryption, and can separate corporate data from personal data. Loss or theft is then a manageable event rather than a breach. The same principle applies to Bluetooth: turn it off when not needed, reject unexpected pairing requests, and keep devices non-discoverable.

E14

Session Security, Hardening, and Exam Guidance

Consolidation

Session hijacking ties the web and network parts of this module together. A stolen token defeats a strong password because the server trusts the token, not the person. Defences are specific: HTTPS everywhere, HttpOnly and Secure cookie flags, long random identifiers, binding the session to a user-agent or device fingerprint, short idle timeouts, and regeneration of the identifier at login and privilege change. Anomaly detection can spot two sessions from distant locations, and a logout should invalidate the token server-side rather than merely deleting the browser cookie.

Secure web-server hardening collects the recurring controls: disable directory listing and default content, remove unused modules, run with least privilege, return generic errors, enforce TLS 1.2 or newer with HSTS, use parameterised queries and output encoding, patch the framework and dependencies, place a WAF in front, and centralise logs. The CSIRT owns detection and response, while the perimeter is layered from edge firewall through IDS/IPS and internal segmentation to host controls and logging. Honeypots contribute by feeding the SIEM real attacker behaviour with almost no false positives.

What to write for 3 marks and for 14 marks

Three marks: give three labelled points. For "three differences between IDS and IPS", write placement, action, and failure mode. Fourteen marks: define, tabulate, explain a mechanism, give a worked example, give defences at several layers, and evaluate. A question on web attacks can cover SQLi and XSS with a type table, a payload or query example, the root cause, the definitive fix, and the supporting controls. A question on incident response can use the six phases with a timeline and an order-of-volatility point.
