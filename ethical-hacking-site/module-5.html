Covering Tracks, Logging & Privilege Escalation

The after-access layer: how intruders erase evidence and hide files, what event logs record and how to protect them, how passwords are cracked and privileges escalated, how persistence survives a reboot, and how a defender rebuilds the timeline and responds to the incident.

01

Covering Tracks & Hiding

Anti-forensics

After gaining access, an attacker erases evidence — disables auditing, clears logs, modifies logs/registry, removes created files/folders. This extends the "maintaining access" phase.

Hiding malicious processes

Run under genuine OS process names; Task Manager shows disproportionate resource use. Covert channels tunnel traffic in overlooked protocols (DNS/ICMP) — indicator = large ICMP/DNS volumes, zone transfers.

Why it matters

Anti-forensics slows incident response and lets the attacker keep access. Defenders rely on logging integrity (see §04).

04

Hiding Evidence on Host & Network

Data hiding

A covert channel hides data while it moves. Data-hiding techniques: hidden partitions, file extensions, hidden attribute, bit-shifting, encryption, password protection.

File manipulation

Names/extensions/hidden attribute (e.g. common with FAT systems; place sensitive info on free space).

Disk manipulation

Hidden partitions; mark a good cluster bad using Norton Disk Edit — type B in the FAT entry for that cluster.

Bit-shifting

Old technique: shift bit patterns to alter byte values so files look like binary executable code. Tool: Hex Workshop.

Steganography

"Hidden writing" — insert data into images/text docs (S-Tools, DPEnvelope, jpgx). Very hard to spot without prior knowledge.

Encryption

Password/passphrase protects files; recovery is hard without it. Key escrow lets data be recovered if a passphrase is forgotten or key corrupted.

Cracking encrypted files

Needs expert + powerful computers, or persuading the suspect to reveal the password.

05

System Hacking: Password Cracking

The kill-chain end

System hacking = using technical skills to gain access, exploit vulns, and conceal activity. The system-hacking cycle (6 steps):

#Step
1Enumeration
2Cracking passwords
3Escalating privileges
4Executing applications
5Hiding files
6Covering tracks

Passwords by character class: letters only · numbers only · special only · letters+numbers · letters+special · special+numbers · all three.

Administrator password guessing

  • If NetBIOS TCP/139 is open, the most effective break-in is password guessing.
  • Connect to an enumerated share (IPC$ or C$) and try username/password.
  • Default Admin$, C$, %Systemdrive% shares are a good starting point.
Password sniffing: instead of guessing, sniff credentials off the wire as users log in, then replay them to gain access.

Manual cracking steps

  1. Find a valid user account (Administrator or Guest).
  2. Create a list of possible passwords.
  3. Rank passwords high to low probability.
  4. Key in each password; repeat until success.

Automated: dictionary or brute-force tools.

06

Privilege Escalation

Footprint → root

Gaining elevated rights beyond what's assigned — via a bug, misconfiguration, or weak access control. Five primary methods: Credential exploitation · Vulnerabilities & exploits · Misconfigurations · Malware · Social engineering.

HHorizontal

Access rights of another account with similar privileges ("account takeover"). Lower-level accounts broaden the attacker's sphere — basic lateral movement.

VVertical

Move from low to higher privilege (e.g. via a buffer overflow) to gain admin/root. Also called a privilege-elevation attack.

Attack chain: gain entry → surveil → escalate → clean up (mask source IP, delete logs). Any evidence of presence = an Indicator of Compromise (IoC).

Hiding & Anti-Forensics in Practice

Techniques

NTFS Alternate Data Streams

type secret.txt > legit.exe:hidden.txt hides data in a file's stream — invisible in normal dir listings.

Timestomping

Altering file MAC times to match legit files and dodge "recently changed" filters.

Hiding evidence by altering event logs

Attackers target Windows event logs (anti-forensic, MITRE T1070) to slow response — clearing them (wevtutil cl <log>) or editing events to erase their own IOAs. This is the syllabus's "hiding evidence by altering event log."

Rootkits

Kernel/user-mode code that hides processes, files, and network connections from the OS.

Defender counter: collect logs off-box (so local wipe loses the copy), use file-integrity monitoring, and snapshot system state for comparison.

E1

Anti-Forensics and the Attacker's Endgame

Deep dive · anti-forensics

Once an attacker has a foothold, their priority changes from getting in to staying in and avoiding attribution. Covering tracks is the collection of techniques used to remove, obscure, or falsify evidence of the intrusion. It is the final phase of the classic kill chain and is mapped in MITRE ATT&CK to the defence evasion tactic, with indicator removal and clearing of event logs as specific techniques. The motivation is practical: a defender who can reconstruct the attack can identify the entry point, close it, and attribute the activity; an attacker who hides the trail can return later through the same door.

Anti-forensics attacks the integrity and availability of evidence rather than the confidentiality of data. The attacker disables auditing, clears or edits logs, alters timestamps, hides files in alternate streams or slack space, removes tools, and may tunnel communications through protocols that monitoring ignores. Each action leaves a second-order trace: disabling auditing produces its own event, a cleared log has a suspicious gap, and a file whose modification time predates the operating system's installation is anomalous and worth investigating (though copied, extracted or restored files can legitimately carry older timestamps). Perfect concealment is hard; the attacker is usually trying to delay discovery long enough to finish the objective.

The defender's response is to make evidence hard to destroy and easy to correlate. Logs are shipped off the host as they are produced, so wiping the local copy does not erase the central one. Clocks are synchronised with NTP so events from many systems line up. File-integrity monitoring detects changes to critical files, and endpoint telemetry records process creation even when an application log is cleared. These controls assume the host is compromised and therefore protect the evidence outside it.

E2

Windows Event Logging in Depth

Deep dive · evidence

An event log is a structured record of activity produced by the operating system, an application, or a device. Windows organises logs into categories, and knowing which category records what is essential for an investigator. The Application log holds events written by programs; the System log holds operating-system and driver events; the Security log holds audited events such as logons and file access; and on domain controllers the Directory Service, DNS Server, and File Replication Service logs hold role-specific records. PowerShell and Windows Defender have their own operational logs that are frequently decisive in investigations.

The Security log is subdivided into categories that map directly to attacker behaviour: account logon and account management, logon events, object access, policy change, privilege use, process tracking, directory service access, and system events. A failed logon burst appears here; so does the creation of a new user, a change to audit policy, and the clearing of the log itself. Event Viewer displays the time, source, event ID, and user, and can filter and export events. Event IDs are the shorthand investigators use: a 4624 records a successful logon, 4625 a failure, 4688 a process creation, and 1102 the clearing of the Security log.

The maximum log size and retention policy determine how much history survives. A small log that overwrites old entries may have lost the evidence by the time an analyst looks. Forwarding events to a central collector as they occur removes that dependency. Investigators also check the audit policy itself: an attacker who disables auditing generates a policy-change event, but if logs are small that record may be overwritten quickly.

Log categoryTypical eventsInvestigative value
SecurityLogons, account changes, policy changesWho accessed what and when
SystemService starts, driver failuresPersistence and crash evidence
ApplicationProgram-specific errorsApplication-layer failures
PowerShell OperationalScript block and command textFileless attacks, encoded commands
Directory ServiceReplication and object changes (DC)Domain-level attacker actions

Worked event sequence

4625  failed logon for user "a.sharma" x 40 from 10.0.0.9
4624  successful logon, same user, LogonType 10 (remote interactive)
4688  process created: powershell.exe -enc ...   (encoded command)

The clearing event is itself proof that someone tried to hide activity.
Because logs were forwarded, the first four events survive on the collector.

E3

Linux and Centralised Logging

Deep dive · visibility

Linux systems produce text logs under /var/log. auth.log or secure records authentication and sudo use, syslog or messages records general system events, and application daemons keep their own files. journald adds structured, indexed logging with metadata that survives reboots when configured to persist. The audit daemon (auditd) watches files, commands, and system calls against rules and produces high-fidelity records suitable for compliance. Web servers write access and error logs that reveal scanning and injection attempts.

Centralised logging follows a simple architecture: agents or native forwarders on each host send events over a protected channel to a collector, which normalises and stores them in a SIEM. The SIEM correlates events across hosts — combining a failed logon, an impossible-travel alert, and a new process on one timeline — which is something no single host can do. It also enforces retention policies and restricts access so that investigators can trust the archive.

Time synchronisation is a hidden dependency of all of this. If one host's clock is wrong by minutes, correlation places events in the wrong order and the story disappears. NTP or an authenticated time source should be mandatory on every system, and timestamps should be recorded in a standard offset. Log integrity can be further protected with signed records or a write-once store.

Fig · Centralised logging architecture
  [ Host A ] --(agent)---\
  [ Host B ] --(agent)----+---> [ Collector ] ---> [ SIEM ] ---> [ Analyst ]
  [ Network devices ]-----/         |                   |
                                    v                   v
                          [ Write-once archive ]   [ Alerts / cases ]

  NTP synchronises every clock so the timeline is coherent.
  The attacker can wipe Host A, but cannot reach the collector.

The central collector is the answer to local log tampering: the host may be fully under the attacker's control, but the copy already shipped off-box is not.

Exam tip: For "how do you defend logs?", give four controls — enable auditing, restrict permissions, forward off-box, and make storage append-only or write-once — and add NTP so timelines remain valid.
E4

Defending Log and Accounting Integrity

Deep dive · hardening

Logs are only useful if they are complete and trustworthy. Six controls protect them. Activate logging with an audit policy that covers logon, object access, policy change, and process creation; a log that is not enabled records nothing. Restrict permissions so ordinary users and service accounts cannot read or modify log files. Separate the logging server so a compromised host cannot reach the stored copy. Encrypt log files in transit and at rest to prevent casual reading and tampering. Use append-only storage so records cannot be edited or deleted without high privilege. For the strongest guarantee, use write-once media or object-lock storage where deletion is impossible until retention expires.

These controls address different attacks. Permissions stop a user from clearing their own trail. Forwarding stops an administrator-level attacker who owns the local machine. Append-only storage stops an attacker who reaches the collector but lacks the privilege to change its policy. Encryption and signatures reveal modification. A programme that implements only one of the six leaves a clear path around it.

Detection rules should watch the log system itself. An event 1102 in Windows, a sudden stop in syslog forwarding, a gap in the sequence of records, or a change to audit policy are all strong indicators. Monitoring the monitor is not paranoia; it is the recognition that anti-forensics is a normal step in a skilled intrusion.

ControlAttack it defeatsLimitation
Enable auditingNo record of the actionGenerates volume that must be tuned
Restrict permissionsLocal user edits logAdministrator can still override
Off-box forwardingLocal wipeNeeds network and agent health
Append-only / object lockDeletion on the collectorRequires storage support and policy
Encryption and signaturesQuiet modificationDoes not prevent deletion
Exam tip: The most complete sentence is "ship logs off the host as they are generated, to append-only storage, with synchronised clocks." It covers tampering, deletion, and correlation in one line.
E5

Hidden Processes and Covert Channels

Deep dive · concealment

An attacker who has executed code wants it to keep running without appearing in the list of processes. Classic approaches run malicious code under the name of a genuine system process, inject it into a legitimate process's memory, or hide it with a rootkit that alters what the operating system reports. A rootkit at user level hooks API calls so a directory listing omits certain files; a kernel-level rootkit can hide processes, drivers, and network connections from every tool that relies on the same operating-system interfaces. The indicator is a mismatch: a CPU or network usage pattern that does not correspond to any visible process, or two tools that disagree about what is running.

A covert channel carries data through a mechanism not intended for communication. DNS is a favourite because outbound DNS is rarely blocked: the attacker encodes commands in subdomain labels and receives answers from a server they control. ICMP tunnels place data in ping payloads. Timing channels vary the interval between otherwise normal packets. These channels are attractive because they blend into allowed traffic, but they have signatures — unusually long subdomain names, high query volumes to one domain, large ICMP payloads, or regular beaconing intervals.

Defences are layered. Egress filtering limits which protocols may leave the network, and DNS filtering blocks known-bad domains. Threat hunting compares process telemetry from different sources, such as the kernel and an endpoint agent, to reveal rootkit discrepancies. Endpoint detection watches for process injection and unusual parent-child relationships. Because covert channels rely on being overlooked, visibility and analytics matter more than a single blocking rule.

Exam tip: A covert channel hides the communication; a rootkit hides the artefacts. Keeping those two ideas separate makes a long answer much clearer.
E6

Data-Hiding Techniques in Depth

Deep dive · concealment

Hiding data is different from encrypting it: the goal is that nobody thinks to look. NTFS alternate data streams let a file carry additional named streams invisible in a normal directory listing; a text file can hide a whole payload in a stream attached to an innocent image. Timestomping changes a file's modified, accessed, and created times so it blends into a folder of old files. Slack space is the unused remainder of a disk cluster, and data written there does not appear in the file's size. Steganography embeds information in the least significant bits of an image or the whitespace of a document, so the carrier looks unchanged to a human.

Encryption is the strongest protection because without the key the data is unreadable even when found, but it has a drawback: encrypted files look suspicious. Key escrow addresses recovery — a copy of the key is held by a trusted authority so data can be recovered if a passphrase is forgotten or a key is lost — but the escrow agent becomes a high-value target and a privacy concern. Cracking encrypted files generally requires either substantial computing power against a weak password or obtaining the passphrase from the owner.

Detection uses specialised tools. Alternate-stream scanners list named streams; file-integrity monitoring catches unexpected changes; timeline analysis finds files whose timestamps contradict the activity around them; steganalysis looks for statistical anomalies in images; and entropy measurement flags files that look random. The practical lesson is that hiding raises the cost of discovery but rarely removes it, so layered logging and integrity monitoring remain valuable.

Worked alternate-data-stream example

C:\> type secret.txt > holiday.jpg:hidden.txt

  Directory listing shows:  holiday.jpg    245,760 bytes
  But the file also carries a named stream "hidden.txt" containing secret.txt.
  Copying the file to a non-NTFS drive strips the stream; forensic tools
  that enumerate ADS reveal it.

  Defender: include ADS-aware scanning in the endpoint checks and alert on
  streams attached to executable or image files.

E7

Password Cracking in Depth

Deep dive · credentials

Cracking is the recovery of a password from a stored hash or by repeated online attempts. Online cracking tries logins against the live service and is limited by rate limiting, lockout, and user behaviour. Offline cracking uses a stolen hash database and can run as fast as the hardware allows, because nobody can lock a file. The strength of the hash function determines the cost: fast general-purpose hashes allow billions of guesses on a GPU, while deliberate password hashes such as bcrypt, scrypt, and Argon2 are tuned to be slow and memory-hungry.

A salt is a random value stored with each hash. Because every user gets a different salt, identical passwords produce different hashes, so a cracked password does not reveal everyone who chose the same value and precomputed rainbow tables become useless. Attackers compensate with wordlists, mutation rules that add common digits and symbols, and hardware acceleration. Pass-the-hash attacks skip cracking entirely by reusing a captured hash where the protocol accepts it, which is why credential guard and restricting local administrator reuse matter.

The manual method taught in the syllabus is deliberately simple: find a valid account, build a ranked list of likely passwords, try each one, and repeat. Automated attacks scale the same idea with dictionaries and rule sets. Defences are length-based password policy, screening against known-breached passwords, unique passwords enforced by a manager, slow salted hashing on the server, multi-factor authentication, and monitoring for many failures or one password tried across many accounts.

E8

The System Hacking Cycle

Deep dive · end to end

The system-hacking cycle ties together the whole course in six steps: enumeration, password cracking, privilege escalation, executing applications, hiding files, and covering tracks. Enumeration collects the names and shares; cracking turns a name into a session; escalation turns a session into administrative power; execution runs the attacker's tools; hiding preserves them; covering tracks removes the evidence. Each step maps to an earlier module and each produces indicators a defender can detect.

Administrator password guessing is a classic version of the second step. If NetBIOS over TCP port 139 is open, an attacker can attempt logins against the administrative shares — IPC$, C$, Admin$, and the system drive — and a default or unchanged password gives immediate access. Manual guessing starts with a valid account such as Administrator or Guest, builds a prioritised list, and tries entries in order. Automated tools perform the same process with dictionaries. The defensive lessons are to rename or disable default accounts, enforce strong unique passwords, close unnecessary ports, and alert on repeated failures against administrative shares.

Worked end-to-end scenario

1 ENUMERATE   SMB null session -> users: a.sharma, svc_backup; share "Finance"
2 CRACK       Offline NTLM hashes -> svc_backup = "Summer2019!" (dictionary rule)
3 ESCALATE    svc_backup is a local admin; token theft yields SYSTEM
4 EXECUTE     Drop a scheduled task that runs a PowerShell downloader hourly
5 HIDE        Payload stored in an NTFS alternate stream of a benign image
6 COVER       Clear the Security log and timestomp the image file

Detections along the way:
  null session attempt, failed logins, new local-admin membership,
  schtasks creation at odd hours, ADS stream, 1102 log-clear event,
  and off-box logs that survive the local wipe.

E9

Privilege Escalation in Depth

Deep dive · from user to admin

Privilege escalation is obtaining rights beyond those assigned to the account. Vertical escalation moves upward, from an ordinary user to administrator or root; horizontal escalation moves sideways into another account with similar rights, which is the basis of lateral movement. The five common causes are stolen or weak credentials, exploitable vulnerabilities, misconfigurations, malware, and social engineering. In almost every case the underlying problem is that the system trusts something it should verify — a token, a file permission, or a service configuration.

On Linux, frequent paths include sudo rules that allow a shell without a password, SUID binaries that run with the owner's privileges and can be abused to spawn a root shell, world-writable cron or service files, and unpatched local kernel vulnerabilities. Enumerating with find / -perm -4000 and reviewing sudo -l are standard first steps. On Windows, paths include token theft from another logged-on user, UAC bypass through auto-elevating binaries, weak service permissions such as an unquoted service path or a replaceable binary, DLL hijacking in a writable application directory, and excessive rights on domain accounts.

Defence starts with prevention: no users in the administrators group by default, patching, application allow-listing, and reviewed sudo or delegated-rights configuration. Detection comes from monitoring privileged-group membership changes, new services, unusual process parents, and administrative activity from ordinary accounts. The principle of least privilege is what makes escalation hard: if a compromised account has almost no rights, there is nowhere to climb.

E10

Persistence After Escalation

Deep dive · maintaining access

Escalation is useful only if the access survives a reboot or a password change, so attackers add persistence mechanisms. On Windows these include entries in the Run registry keys, scheduled tasks, new services, startup-folder shortcuts, WMI event subscriptions, and domain-level changes such as a new account or a golden ticket. On Linux they include cron jobs, systemd units, modified shell profiles, and authorised SSH keys. Each mechanism has a matching detection source: Sysmon and Security event ID 4698 for scheduled tasks, registry monitoring for Run keys, auditd rules for cron and profile changes, and identity reviews for new privileged accounts.

Persistence is closely related to covering tracks but is not the same. Persistence ensures the attacker can return; covering tracks ensures nobody learns they were there. An attacker who achieves the first without the second is noisy but durable; one who achieves the second without the first is hidden but may lose access after a reboot. Skilled attackers do both, which is why incident response must search for persistence even when logs appear clean.

The defensive approach is to treat change as suspicious. Baseline the set of services, scheduled tasks, startup entries, and privileged accounts, then alert on additions. Restrict who can create services or write to startup locations. After an incident, rebuild from a trusted image rather than merely deleting the discovered artefacts — an attacker may have more than one mechanism.

E11

Covering Tracks, Step by Step

Deep dive · anti-forensics

A typical track-covering sequence begins by disabling or reducing auditing, then clearing or editing the event logs that recorded the intrusion, then deleting or timestomping dropped files, then removing accounts and tools, and finally restoring any configuration that was changed. In Windows a log can be cleared with wevtutil cl <logname>; in Linux an attacker may truncate /var/log/secure or delete shell history. Each action is detectable: disabling auditing and clearing a log are themselves events, truncation creates an obvious gap, and deleted files leave artifacts in the filesystem.

Attackers make predictable mistakes. They clear the Security log but forget the PowerShell or Defender operational log. They timestomp a payload but leave its creation time in the Master File Table inconsistent. They delete a tool but forget the scheduled task that launches it. They work quickly and generate anomalies that stand out against normal behaviour. The defender's advantage is that an intrusion touches many systems, and the attacker must hide all of the traces; the defender needs to find only one.

The operational response is to collect volatile evidence first, preserve the original logs, compare multiple telemetry sources, and build a timeline. File-integrity monitoring and off-box forwarding mean the attacker's local cleanup has no effect on the central copy. The investigation should finish with a gap analysis: which logs were missing, which control failed, and what change will close it.

E12

Detection, Response, and Exam Guidance

Consolidation

Module 5 is the defender's view of the attack endgame. The attacks are anti-forensics, hiding, credential theft, and escalation; the defences are trustworthy logging, integrity monitoring, least privilege, endpoint telemetry, and a rehearsed incident-response process. The connecting idea is that every attacker action changes something: a log is cleared, a timestamp moves, a token is used from a new location, a new service appears. Detection is the practice of noticing those changes, and response is the practice of acting before the attacker finishes the objective.

What to write for three marks: give three labelled points. For "three ways attackers hide evidence", write alternate data streams, timestomping, and steganography, each with a six-word description. What to write for fourteen marks: define the terms, use the six-step system-hacking cycle as a structure, give a worked command or timeline, provide a table of techniques and indicators, explain both preventive and detective controls, and close with the incident-response phases.

Module glossary

Anti-forensics — techniques that remove or falsify evidence. Covert channel — communication through an unintended mechanism. Alternate data stream — hidden data attached to an NTFS file. Timestomping — altering file timestamps. Steganography — hiding the existence of a message. Salt — random data added before hashing a password. Vertical escalation — moving to higher privilege; horizontal — moving to another account at the same level. Persistence — a mechanism that survives reboot. IoC — an indicator of compromise. Order of volatility — collecting fragile evidence first.

Final exam tip: End every Module 5 answer with the defender's architectural answer — centralised, append-only logging with synchronised clocks and endpoint telemetry — because it defeats hiding, escalation concealment, and track removal at the same time.

Investigation Scenarios

Worked practice

Scenario A — the cleared log that did not disappear

An administrator notices that the Security log on a file server ends abruptly at 02:14. The local log shows no events after that time, and the maximum size has not been reached. Rather than assuming the server simply stopped logging, the analyst checks the collector. It holds hundreds of events from the same host after 02:14, including a 4688 process creation for a script interpreter and a 4624 logon with an unusual account. The timeline from the collector shows that someone ran wevtutil cl Security moments after the suspicious process started. Because forwarding was configured, the attacker wiped only the local copy. The investigation proceeds from the surviving central records, the host is isolated, and the account is disabled. Lesson: a gap in a local log is an indicator, not the end of the evidence.

Scenario B — the password that was never cracked

A user reports that files in a shared folder were encrypted overnight. The obvious suspicion is that an attacker cracked the user's password, but the authentication logs show only normal logins from the usual device. Further analysis finds that the user had authenticated to a compromised workstation earlier in the day, and a high-privilege token from that session was reused to access the share. No offline cracking was required; the attacker rode an existing authenticated session. The response therefore includes revoking all tokens, rebuilding the workstation, reviewing where privileged accounts are allowed to log on, and training users not to enter credentials on shared systems. Lesson: not every credential attack involves guessing passwords; token reuse bypasses the whole cracking problem.

Exam tip: Worked scenarios earn marks when you state what the analyst checked, what the evidence showed, and which control would have prevented it. Use the pattern "symptom → evidence → root cause → control" for each one.

Revision Checklist and Common Mistakes

Exam technique

Before the exam, be able to do the following without notes: name the six default Windows event-log categories and three Security-log subcategories; explain the difference between horizontal and vertical privilege escalation with one example each; describe at least four data-hiding techniques and one detection method for each; explain why salting and slow hashes defeat offline cracking; recite the six steps of the system-hacking cycle; and state the six incident-response phases in order. For each item, attach one indicator and one control so that every definition is usable in an application question.

Common mistakes are predictable. Students often say "encryption" when the question is about hiding existence, confuse clearing a log with preventing logging, describe a rootkit as a password-cracking tool, forget that covering tracks generates its own events, and answer a privilege-escalation question with generic antivirus advice. Another frequent error is to treat event logs as a single undifferentiated file; naming the category and subcategory shows that you understand where evidence lives. Finally, many answers omit the defender's architectural control — off-box, append-only logging with synchronised time — which is the strongest closing point available in this module.

MistakeCorrection
"Encryption hides the file"Encryption hides meaning; steganography hides existence
"Clearing logs stops logging"Clearing removes records; disabling auditing stops new ones
"Rootkits steal passwords"Rootkits hide processes, files and connections
"Escalation means installing malware"Escalation means gaining rights beyond those assigned
"Local logs are enough"Forward them off-box to append-only storage
Exam tip: Spend the last revision session on the pairings — attack, indicator, control. They convert recall into marks faster than rereading prose.
